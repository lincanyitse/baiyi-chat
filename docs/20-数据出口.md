> 文档编号：BY-DOC-20

> 上游：[17-Web产品规格](./17-Web产品规格.md) §1.3 · [18-Web产品路线图](./18-Web产品路线图.md) v0.2

## 1. 为什么这是 v0.2 的第一优先

企划书 §1.3 写的是「数据属于自己」。但如果数据拿不出来，这条原则只是口号：

| 现状 | 后果 |
| --- | --- |
| 没有会话导出 | 用户被锁在界面里，想带走对话只能截图 |
| 没有用户可触发的备份 | 只有迁移前会自动备份，用户不知道、也拿不走 |
| 备份只复制 `.db` | WAL 模式下会漏 `-wal`，恢复后丢最近的写入 |

**数据丢失与数据锁定都不可逆**，优先级高于任何「用起来更顺」的功能。

## 2. 现状核查

### 2.1 已有的

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 迁移前自动备份 | `sqlite.go:246` `backup()` | 复制到 `backups/`，用户无感也无入口 |
| 消息分支树 | `messages.parent_id` | 支持多分支，导出要考虑 |
| 会话/消息/轮次查询 | `Repo.ListSessions` / `ListMessages` / `ListTurns` | 导出的数据来源就绪 |

### 2.2 缺的

| 项 | 说明 |
| --- | --- |
| 会话导出 | 无 Markdown、无 JSONL |
| 用户触发备份 | 无接口、无界面 |
| 备份恢复 | 无 |
| WAL 处理 | `backup()` 只复制主文件 |

**`backup()` 的具体缺陷**：WAL 模式下最近的写入可能还在 `-wal` 文件里。
只复制 `.db` 会得到一个"看起来正常但少了最后几轮对话"的备份——这比没有备份更危险，
因为用户会以为数据保住了。

## 3. 设计

### 3.1 会话导出：两种格式，各有明确用途

#### Markdown（给人看）

```markdown
# 会话标题

> 导出时间：2026-11-10 14:30 · 12 轮对话 · 模型：anthropic/claude-sonnet

## 用户

帮我解释一下这个函数

## 助手

这个函数做三件事……

<details>
<summary>工具调用：rag_search</summary>

**参数**：{"query": "函数用法"}

**结果**：……

</details>
```

**分支怎么处理**：主链按 `seq` 顺序导出；被丢弃的分支折叠进
`<details>` 附在分叉点之后，标注「未采用的回答」。这样既不丢内容，
也不让正文变成一团乱麻。

**工具调用**：默认折叠。正文是模型说的话，工具细节是过程，不该抢注意力。

#### JSONL（给程序读）

每行一个 JSON 对象，字段与 `StoredMessage` 对齐：

```json
{"type":"session","id":"...","title":"...","created_at":"...","model_ref":"..."}
{"type":"message","id":"...","seq":1,"parent_id":null,"role":"user","content":[...],"created_at":"..."}
{"type":"message","id":"...","seq":2,"parent_id":"...","role":"assistant","content":[...],"created_at":"..."}
```

第一行是会话元数据，之后每行一条消息。**保留 `parent_id` 与原始 `content` 结构**——
这是「能重新导入」的前提。

### 3.2 备份：用 SQLite 自己的方式，不是复制文件

`VACUUM INTO 'path'` 是 SQLite 官方的一次性快照方案：
它在一个读事务里写出完整数据库，自动包含 WAL 中已提交的内容，且产出的是
一个干净、已整理、无 WAL 依赖的单文件。

```
POST /api/backup
→ {"path": "<数据目录>/backups/baiyi-20261110-143000.db", "size": 1234567}
```

**不做 zip 打包**：数据库单文件已经足够，打包只是多一层用户要解压的东西。
密钥密文在库里，但数据密钥被 DPAPI 绑定当前用户——备份拷到别的机器解不开，
这正好是想要的（ADR-0020）。

#### 恢复

**不在界面里做**。理由：

1. 恢复需要关闭数据库、替换文件、重启进程——在运行中的进程里做等于自杀
2. 恢复错了的后果是覆盖现有数据，需要极强的二次确认，而命令行更合适

提供 `baiyi restore <备份路径>` 子命令：

```
1. 校验目标是一个 SQLite 库（PRAGMA integrity_check）
2. 把当前库改名为 baiyi.db.before-restore-<时间戳>
3. 复制备份到 baiyi.db
4. 提示用户启动
```

**备份文件保留现状**：当前的 `.bak` 命名已包含时间戳，改名即可。

### 3.3 导出入口

| 位置 | 形式 |
| --- | --- |
| 单个会话 | 会话列表右键 / 会话标题旁的菜单 → 「导出为 Markdown」/「导出为 JSONL」 |
| 全部会话 | 「设置 → 数据」页 → 「导出全部会话（JSONL）」 |

浏览器下载：服务端返回 `Content-Disposition: attachment`，
文件名用会话标题（清洗掉非法字符）。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/sessions/{id}/export?format=md\|jsonl` | 下载单个会话 |
| `GET` | `/api/export?format=jsonl` | 下载全部会话 |
| `POST` | `/api/backup` | 立即备份，返回路径与大小 |
| `GET` | `/api/backups` | 列出已有备份（路径、大小、时间） |

## 5. 安全

| 威胁 | 防护 |
| --- | --- |
| 路径穿越（导出文件名） | 文件名只用于 `Content-Disposition`，不参与路径拼接 |
| 备份路径被注入 | 备份目录由服务端固定，接口不接受路径参数 |
| 导出泄露密钥 | 导出只读 `messages` 表，不碰 `provider_secrets` |
| 恢复覆盖错数据 | 先改名保留旧库，再复制；两步都成功才报告完成 |

## 6. 验收

| 项 | 验证 |
| --- | --- |
| Markdown 导出 | 含分支的会话导出后，主链在正文、分支在折叠块 |
| JSONL 往返 | 导出 → 解析 → 消息数与 `parent_id` 链与库内一致 |
| WAL 完整性 | 写入后立刻备份，备份里能看到最后一条消息 |
| 备份可用 | 备份拷贝到同用户另一目录，`baiyi restore` 后能正常打开 |
| 恢复保留旧库 | 恢复后存在 `baiyi.db.before-restore-*`，可回退 |
| 空会话 | 导出空会话不报错，产出合法的空结构 |

## 7. 不做

| 项 | 理由 |
| --- | --- |
| 内置 zip 打包 | 单文件已够；多一层解压是负担 |
| 自动定时备份 | 增删改策略要调，先让用户能手动触发 |
| 云同步 / 网盘 | 数据留在本机是核心价值 |
| 界面内恢复 | 需要停库换文件，命令行更安全 |
| 导入 JSONL 回会话 | 有价值但独立：导入要处理 ID 冲突、时间戳、分支合并 |

## 8. 实施记录

已实现。实施中发现并修掉的问题：

| 问题 | 处理 |
| --- | --- |
| `restore` 的 `--data-dir` 不生效 | Go 的 flag 在遇到第一个非 flag 参数后停止解析，`baiyi restore X --data-dir Y` 中的 flag 被当成位置参数。补手动提取，两种写法都支持 |
| 保留的旧库缺 `-wal` | 只改名 `.db` 会得到一个少了最后几轮的「备份」，回退时救不回来。WAL/SHM 一并改名 |
| 写回累积空行 | 已在 ADR-0021 修复（配置写回），本模块不受影响 |

**恢复时的一个真实风险已消除**：验证过程中误把 `--data-dir` 失效当成正常，恢复写到了默认数据目录。
现在 `--data-dir` 位置无关，且 `Restore` 会保留原库（含 WAL），最坏情况可以换回来。
