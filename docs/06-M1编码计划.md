## Context

M0 让白泽能对话、能持久化、能记账、能看日志，但**不能干活**——模型返回的 `ToolCallReady` 事件被收进 `TurnResult.ToolCalls` 后就丢弃了，永远不会被执行。

M1 要补上这一环：Agent Loop、工具执行、审批、上下文组装、技能、MCP。这是从「聊天机器人」到「助理」的转折点。

15 项交付物估计 15–20 人日，一次性做完风险太大，拆成 **M1.1（能干活）** 与 **M1.2（稳态与扩展）** 两个里程碑。

### 已确认的决策

| 维度 | 决策 | 理由 |
| --- | --- | --- |
| 拆分 | M1.1（Loop + 工具 + 审批 + 上下文）→ M1.2（技能 + MCP + 摘要 + Trace） | 早点看到端到端效果，降低返工风险 |
| `web_search` | 抽象为**可插拔后端接口**（千问 / DeepSeek / 自部署），未配置时返回明确错误 | 不绑定单一搜索服务商 |
| 审批交互 | REPL 终端 y/n；M3 再加 Web 弹窗版 `Approver` | M1 只有 REPL 一个渠道 |

### 三个必须先修的阻塞缺口（已核实）

| 缺口 | 现状 | 影响 |
| --- | --- | --- |
| `llm.Request` 无 `Tools` 字段 | 三适配器只解析 tool_call，无法发送工具定义 | **头号阻塞**：不做则模型永远不知道有哪些工具 |
| `Request.CacheBreakpoints` 未被读取 | `grep` 只命中定义处，Anthropic `cache_control` 未实现 | 前缀缓存失效，每轮成本翻倍 |
| `registry.Resolve` 无候选链 | 只取第一个能构造的 Provider，无降级、无健康度 | FR-PRV-008/009 无法验收 |

`Candidates()` 已能返回有序候选链，改造 `Resolve` 是纯加法。

## 包结构与边界

### `session.Ask` 拆解

现状：`Ask` 有 155 行，同时做建 turn、读历史、落消息、调模型、消费事件、记账、生成标题、错误处理。

| 逻辑 | 去向 | 理由 |
| --- | --- | --- |
| 建 turn、更新状态、`TouchSession`、首轮标题 | **留 session** | 持久化权威，且要保证幂等 |
| 历史读取/缓存/失效 | **留 session** | 现有实现已优化，不动 |
| 消息 append（含 `NextSeq`） | **留 session**，经 `agent.Store` 暴露 | 唯一写入方，缓存一致性靠它 |
| 调 Provider、消费事件流、判定 StopReason | **移 agent** | M1 要循环调用，不能再写死在一次 Stream 里 |
| 步数/墙钟/成本预算、取消传播 | **移 agent** | 属于运行时职责 |
| 记账 `ledger.Record` / `Compute` | 留 session，agent 经 `Store.RecordUsage` 上报 | 账本仍归 session |

改造后 `Ask` 约 40 行：建 turn → 组装 `agent.TurnInput` → `engine.Run()` → 落终态。

**依赖方向**：`session`（L4）可 import `agent`；`agent` 不 import `session`。`agent` 定义消费方接口 `agent.Store`，`session` 用 `Repository` 实现它——`store/sqlite` 仍只 import `session`+`llm`，耦合不扩散。

`TurnResult` 移到 `agent`，`session.TurnResult = agent.Result` 别名保持 REPL 兼容。

## 关键设计决策

### 1. 状态机：显式枚举 + switch

```go
type state int

const (
    stIngest state = iota
    stAssemble
    stInfer
    stDecide
    stExecute
    stRefill
    stFinalize
    stPersist
)
```

每个 `step()` 只做一次状态转移。理由：状态只有 8 个、需要可测试的转移边界；函数链会把「当前在哪一步」藏进闭包，续跑与快照都无处挂钩。

**挂起不阻塞 goroutine**：写 `approvals` 行 + `turns.status='awaiting'` 后**返回**，下次用户输入或 `/resume` 起新 goroutine 恢复。

**续跑不用状态快照**：transcript 是 append-only 步骤日志，`tool_results` 是幂等缓存，恢复算法是纯函数——「取最后一条含 `tool_use` 的 assistant 消息，缺 `tool_result` 的调用按序重放，再进下一次 Infer」。预算计数只需 `turns.step` / `spent_tokens` 两列。

这比持久化状态机少一张表，且天然自愈——`state_json` 腐化是经典坑。

### 2. 并发：errgroup + 每工具信号量

不建 worker pool：工具少、批量小，pool 只增加调度延迟。

```go
out := make([]toolOutcome, len(calls))
g, gctx := errgroup.WithContext(ctx)
sem := map[string]chan struct{}{} // 按工具名限流
for i, call := range calls {
    i, call := i, call
    g.Go(func() error {
        defer func() {
            if r := recover(); r != nil {
                out[i] = toolOutcome{err: fmt.Errorf("panic: %v", r), stack: debug.Stack()}
            }
        }()
        out[i] = runOne(gctx, call)
        return nil // 工具失败不取消同批其他工具
    })
}
g.Wait()
```

结果**按下标写预分配切片**，`g.Wait()` 提供 happens-before——不需要 channel 收集再排序。

`!caps.ParallelTools` 时退化为串行，走同一代码路径（信号量容量设为 1）。

### 3. 上下文组装：固定 8 段 + 有序降级切片

八段即 `[]Segment`，`Order` 固定。

降级顺序编码为包内**有序切片**，不注册、不插拔：

```go
var degradeChain = []struct {
    name string
    apply func(*plan) (changed bool, trims []Trim)
}{
    {"drop-rag", dropLowestRAGRAG},
    {"shrink-profile", shrinkProfileCard},
    {"stub-tool-results", stubToolResults},
    {"rollup-summary", rollupSummary},
    {"drop-oldest-turns", dropOldestTurns},
    {"fail", failExplicitly},
}
```

架构要求「严格按序不可跳步」，可配置化就是给未来制造漂移。

**快照存储**：段元数据进 `context_snapshots.segments_json`；正文 >2KB 时进 `blobs`（sha256 内容寻址 + `ref_count`），≤2KB 内联。既避免快照撑爆数据库，又不引入对象存储。

**缓存断点**：候选为「第 3 段末」「历史段末」「当前输入前一条」，从后往前取，要求前缀累计 token ≥ `caps.MinCacheTokens`，最终截取最后 4 个并升序。

### 4. 审批：懒检查 + 不阻塞

`expires_at` 懒检查，不启后台 ticker：

- 进程活着时：REPL 侧 `context.WithTimeout(10m)` 到点返回 deny
- 进程死了重启时：任何查询前先扫 `status='pending' AND expires_at < now`，批量置 `expired`，并把拒绝原因作为 `tool_result` 回填

`approve-forever` 只对 `RiskWrite` 开放，`RiskDangerous` 强制 `once`（FR-TOL-002）。

### 5. MCP：官方 SDK + 锁版本

选 `modelcontextprotocol/go-sdk`（v1.8.0）——协议演进由官方跟进。

风险是 API 较新，**锁精确版本 + 全部调用关在 `mcp.Client` 接口后**，换库只改一个文件。

**Windows 特别注意**：

- `exec.Command` 无法直接执行 `npx.cmd`，必须 `cmd /c` 包装
- 需 `SysProcAttr{HideWindow: true}`（build tag `windows`）
- 子进程树用 `CREATE_NEW_PROCESS_GROUP` + `taskkill /T /F` 收尸，否则父进程退出后 node 残留

**名字映射**：内部 `mcp__<alias>__<tool>`；超 64 字符或含非法字符时映射为 `mcp_<alias>_<hash>`（FNV-32a 确定性、双向、持久化到 `mcp_servers.tools_json` 反查），冲突时加别名后缀而非静默丢弃。

### 6. 技能：目录指纹热加载

不做 fsnotify：每轮 Assemble 前对 `skills/` 做 `ReadDir`，比对**内容哈希**。

不用 mtime 做主判据——Windows 上同秒改写的 mtime 不可靠。

另给 `/skills reload` 手动命令。

`load_skill` 的正文**以 `tool_result` 形式入上下文**，不写进 system——否则每次加载都让段 2 变化、整段前缀缓存失效。这是渐进披露能成立的前提。

### 7. web_search：可插拔后端

```go

```

配置驱动：


### 8. SSRF：自定义 DialContext

```go
func safeDialContext(ctx context.Context, network, addr string) (net.Conn, error) {
    host, port, err := net.SplitHostPort(addr)
    if err != nil {
        return nil, err
    }
    ips, err := net.DefaultResolver.LookupIPAddr(ctx, host)
    if err != nil {
        return nil, err
    }
    for _, ip := range ips {
        if isBlocked(ip.IP) {
            return nil, ErrBlockedAddress
        }
    }
    // 固定为校验过的字面 IP，防 DNS rebinding
    return (&net.Dialer{}).DialContext(ctx, network, net.JoinHostPort(ips[0].IP.String(), port))
}
```

`isBlocked` 覆盖：私网（10/8、172.16/12、192.168/16）、环回、链路本地（169.254/16，含云元数据 `169.254.169.254`）、CGNAT（100.64/10）、IPv6 ULA（fc00::/7）、组播；`::ffff:` 前缀先归一化为 IPv4。

**TLS SNI 不受影响**：URL 仍是域名，`DialContext` 只改连接目标，SNI 由 `req.URL.Host` 决定，无需碰 `TLSClientConfig`。

**重定向**：`CheckRedirect` 限制 5 次 + 只允许 http/https + 拒绝带 userinfo 的 URL；每一跳自动再校验（DNS rebinding 防线在此）。

**响应体**：`io.LimitReader(5MB+1)` 超限报错（NFR-SEC-007），总超时 30s。

## 风险与预案

| 风险 | 早期信号 | 预案 |
| --- | --- | --- |
| 改 `Request` + 三适配器打穿 M0 绿测 | adapter payload 测试大面积红 | `Tools` 纯增量、`caps.Tools=false` 不发送；先加 payload golden 再改代码；只在阶段 A 做一次 |

| MCP stdio 在 Windows 失控 | `node.exe` 残留、stdio 卡死 | 先只交付 Streamable HTTP；stdio 走 `cmd /c` + 进程组 + `taskkill /T`；整段可后移 |

**实施中发现的真实缺陷**（均已修复）：

1. **迁移不幂等**——`ALTER TABLE ADD COLUMN` 重跑会因重复列失败。
   迁移中途崩溃重试是真实场景，改为执行前查列是否存在。
2. **段级配额被总预算掩盖**——RAG 用了 2110 token 而配额 515，
   因总量未超预算而不裁剪，配额形同虚设。
3. **本轮工具往返未计入快照**——快照显示「历史 4 token」，
   而模型实际收到了完整往返，诊断信息失真。
4. **污点追踪失效**——`tainted()` 成了死代码；正确语义是
   「接触外部内容后，先前授予的永久允许不再可信」。
5. **panic 的工具漏写幂等缓存**——续跑时会被重复执行。
6. **`ask_user` 拿不到 Approver**——`ExecContext.Approver` 恒为 nil。
7. **控制台日志走 stdout**——打断 REPL 对话输出，改为 stderr。

**与计划的偏差**：

- 阶段 B 的「Provider 健康度与冷却」推迟到 M1.2 的 D 阶段：
  M1.1 只需要候选链能取到第一个可用 Provider，健康度是稳态优化。
- 阶段 C 的「token 估算 EWMA 校准」未做：`llm.EstimateTokens`
  已经零分配且在 50 轮对话下仅 10µs，M1.2 有了真实 usage 数据后再校准更准。
