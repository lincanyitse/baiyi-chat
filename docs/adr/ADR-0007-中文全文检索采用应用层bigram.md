# ADR-0007：中文全文检索采用应用层 bigram 影子列

- 状态：已定稿（M0 冒烟验证通过，2026-11-07）
- 关联：需求 FR-RAG-007、OQ-001；架构纲要 §7.2

## 背景

RAG 需要中文关键词检索。FTS5 内置分词器（`unicode61`）对 CJK 文本按单字切分，多字词的短语语义完全丢失：

- 实测：查询「白泽助手」在默认分词下命中 0 行（样本中确有含该词的文档）。
- `CGO_ENABLED=0` 的前提下无法编译自定义分词器扩展。

## 决策

采用**应用层 bigram 影子列**：

- 写入侧：把中文文本切成相邻二字（「白泽助手」→ `白泽 泽助 助手`），写入 FTS5 表的独立影子列（如 `text_bi`），原文列保留。
- 查询侧：查询串做同样切分后，**必须用双引号包裹成 phrase** 再 MATCH。不加引号时 unicode61 会把 bigram 串拆成多个独立 token 做 AND/OR 匹配，产生误命中。

## 冒烟结论（scratch/fts5-smoke，modernc.org/sqlite v1.61.1，CGO_ENABLED=0）

| 验证项 | 结果 |
| --- | --- |
| FTS5 可用性 | ✅ modernc 驱动编译内置 FTS5，无需额外开关 |
| 默认分词「白泽助手」查询 | ❌ 命中 0（预期失败，证实问题存在） |
| bigram「白泽助手」「会议纪要」「记忆系统」 | ✅ 均命中正确文档 |
| phrase 语义（含「白天泽木」干扰行） | ✅ 只命中真实含「白泽」的行，干扰行不命中 |
| 查询耗时 | ✅ <1ms（样本极小；NFR-PERF-003 的 10 万 chunk 验证在 M2 做） |
| 英文混合内容 | ✅ unicode61 对英文正常分词，可与 bigram 列共存 |

已知取舍：

- bigram 影子列约为原文 2 倍体积（每个字出现在两个 token 中）。
- 单字查询（如「泽」）在 bigram 列无独立 token，需回退到原文列的 LIKE 或默认列 MATCH。
- 跨 bigram 边界的误命中理论上存在于 phrase 内部（如「天泽」命中「白天泽木」），但这是 phrase 级精确匹配的固有属性，召回质量远好于默认分词。

## 后果

- M2 的 RAG 索引按此方案实现；`chunks_fts` 表加 `text_bi` 影子列。
- 切分与查询封装为一个 `bigram.go` 工具模块，写入与查询强制走同一函数。
- 若未来语料达到 10 万 chunk 且性能不达标，再评估外部向量库 + 倒排服务的组合（OQ-008）。
