# ADR-0019：形态路线改为产品矩阵

- 状态：已定（2026-11-10）
- 关联：取代 ADR-0009；影响 01-企划书 §5、02-需求文档 §8、03-架构纲要 §15.4
- 前置：M0–M3 已完成（内核 + Web 基础），M4 桌面探索另存 `feature/desktop-m4`

## 背景

ADR-0009 把形态排成一条线：**内核 → Web → 桌面 → CLI → Bot**，每个形态是一个里程碑（M3/M4/M5/M6）。

M0–M4 走完这一遍后，暴露出两个问题：

**1. 「功能完成」被当成了「产品完成」。**

M3 的 13 项交付物完成 10 项、M4 的 7 项完成 6 项，两份完成报告都打了勾。但实际把 Web 当产品用一遍，发现的是：设置口令后登录页白屏、一个 Provider 都没配时轮次永久卡死、会话过期后不会重新登录、成本永远是 0（因为价格填不进去）。这些不是「没做的功能」，是「做了但用不了」。

**2. 里程碑串行化掩盖了产品之间的独立性。**

把桌面排在 Web 之后，隐含了「Web 定型了才能做桌面」的假设。实际上桌面的核心（托盘常驻、双击启动）与 Web 的功能完整度几乎无关；反过来，Web 的产品化打磨也不需要等桌面做完。串行只会让两件事互相阻塞。

M4 的实践印证了这一点：一边补 Web 的产品化缺口，一边做桌面托盘，最后哪边都不完整。

## 决策

**内核是一次性投入；之后是三个并列的产品，各自独立排期与验收。**

```
内核（已完成）
  M0 地基 → M1 Agent → M2 记忆与 RAG
        │
        ├── Web 产品      ← 当前主攻
        ├── 桌面产品      ← 探索暂存（feature/desktop-m4）
        ├── CLI 产品
        └── Bot 产品
```

四点具体含义：

**1. 内核的完成标准不变**：能对话、调工具、有记忆、能检索。这部分已经达成，之后只做维护性改动。

**2. 每个产品有独立的「产品定义」**：用户是谁、解决什么问题、怎么算成功、不做什么。放在 `docs/products/<product>/` 下，不混进需求库。

**3. 产品的完成标准是「用户体验闭环」，不是「功能清单打勾」。** 一个产品可以功能齐全但没做完（登录页白屏就是例子），也可以功能不全但可用（v0.1 只做对话就能用）。

**4. M3/M4 的编号冻结为历史。** 它们是「内核 + Web 雏形」与「桌面探索」的开发记录，不再作为路线图的一部分。

## 后果

**文档结构**：
- `01-企划书` §5 的「形态演进路线」改为「产品矩阵」
- `02-需求文档` §8 的七个里程碑节改为「内核（已完成）+ 四个产品」
- 需求表的「里程碑」列改为「产品」列；M3/M4 的标注保留但语义变为「该需求首次由哪个产品落地」
- 01–16 号文档冻结，新增从 17 起

**代码结构不变**：`internal/channel/{repl,web}` 的分层本来就是按渠道组织的，与这条决策一致。桌面/CLI/Bot 将来各自新增 `channel/` 下的包即可。

**M4 的处置**：
- 桌面相关（托盘、desktop 模式）→ 留在 `feature/desktop-m4`，属桌面产品线
- 与 Web 相关的部分（扩展管理、重放、附件 GC、子代理、隐私模式）→ **一同回退**，Web 产品需要时按产品优先级重新引入，而不是继承 M4 的实现

最后一条代价最大，但理由充分：M4 的这些功能是在「里程碑思维」下做的——按计划清单实现，没有问过「用户真的需要现在有吗」。重新引入时会带着产品视角重新评估。

## 不改变的

- 单用户、本地运行、模型无关的定位
- 分层单向依赖与「接口只开 6 组」
- `CGO_ENABLED=0` 单二进制分发
- 数据属于自己（本地文件、可完整导出）

## 备选方案与为什么不选

| 方案 | 不选的理由 |
| --- | --- |
| 保持 ADR-0009，只是把 M4 做完再做 M5 | 已经证明会导致「功能清单打勾即完成」，问题会在 M5/M6 重演 |
| 把 Web 拆成 M3.4/M3.5 继续编号 | 编号只能表达「先后」，表达不了「这是另一条产品线」 |
| 只做 Web，砍掉桌面/CLI/Bot | 三者各有明确场景（桌面=常驻、CLI=脚本、Bot=随身），砍掉会失去产品矩阵的价值 |
