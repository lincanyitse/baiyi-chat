# ADR-0020：API Key 加密存储

> 状态：已定
> 日期：2026-11-10
> 关联：[17-Web产品规格](../17-Web产品规格.md) · [18-Web产品路线图](../18-Web产品路线图.md)

## 背景

Web 产品的核心断言是「打开就能问」。但密钥只能通过环境变量注入
（`config.go` 的 `ResolveAPIKey` 只读 `os.Getenv`），`internal/` 下零加密实现。
这让「在页面里配置模型服务商」这条路是断的——普通用户没有终端，
更不会去设环境变量。

## 决策

| 项 | 决定 |
| --- | --- |
| 存储位置 | SQLite 新表 `provider_secrets`，不写回 TOML |
| 加密方式 | 数据密钥（32 字节）+ AES-256-GCM 加密 API Key |
| 数据密钥保护 | Windows：DPAPI，绑定当前用户；其他平台：文件 inode + 设备号绑定 |
| 优先级 | 环境变量 > 加密存储 |
| 丢失处理 | 显式重置入口，二次确认 |

### 为什么分两层

```
API Key  --AES-256-GCM(数据密钥)-->  密文（存库）
数据密钥  --DPAPI / 文件绑定------->  保护后的密钥（存库）
```

直接用 DPAPI 加密每个 Key 也能工作，但：

1. DPAPI 每次调用有系统开销，Provider 多了启动会慢
2. 数据密钥可以缓存进内存，加解密走 AES-GCM（微秒级）
3. 将来换保护方式（比如引入主密码）时，只需重新包裹数据密钥，
   所有密文不用重新加密

### 为什么不写进 config.toml

1. 配置文件是纯文本，用户可能放进 git、云盘或发给别人求助
2. `SaveProviders` 会重写整段 provider，密钥随之落到文件系统
3. 配置是「声明」，密钥是「凭证」——混在一起会让「导出配置」变成「泄露密钥」

## 平台差异

### Windows：DPAPI

`CryptProtectData` / `CryptUnprotectData` 绑定当前用户，换用户或换机器都解不开。
不用 `CRYPTPROTECT_LOCAL_MACHINE`——那会让同机任何用户都能解密。

### Linux / macOS：文件绑定

数据密钥文件 `<数据目录>/secret.key`，保护密钥由文件自身的身份派生：

```
保护密钥 = HKDF-SHA256(Dev:Ino, salt=文件头部 16 字节随机值)
```

- 文件被复制到别处（新 inode）→ 解不开
- 文件被移动（同设备内 inode 不变）→ **仍可用**
- 文件被替换 → 解不开
- 内容被改动 → GCM 认证失败

**为什么不用 mtime**：时钟漂移、解压工具、云同步都会改 mtime，误伤概率高。

**诚实说明**：这不是「加密」，是「防止文件被搬走」。同机有权限读 inode
的进程仍能重建密钥。界面上如实写清，不给超出实际能力的承诺。

## 密钥来源优先级

```
1. 环境变量（Provider.APIKeyEnv 指向的变量）
2. 加密存储
3. 空
```

环境变量优先是给高级用户的显式选择；也让 CI / 容器场景能绕过加密存储
（那些环境里没有 DPAPI）。

## 接口约定

- `GET /api/providers` 返回 `has_key` 与 `key_source`（`env` / `stored` / `none`）
- **永不返回明文**，连脱敏前缀也不返回——长度与格式同样会泄露信息
- `PUT /api/providers` 的 `api_key` 非空表示写入；留空表示「不修改」；
  `clear_key: true` 才是显式清除
- `POST /api/providers/secrets/reset` 清空全部密钥并重新生成数据密钥
- `GET /api/providers/secrets/status` 报告保护方式，供界面说明强度

## 安全边界

| 威胁 | 防护 |
| --- | --- |
| 数据库文件被拷走 | AES-GCM 密文；数据密钥被 DPAPI 绑定，换机器解不开 |
| 同机其他用户 | DPAPI 按用户隔离；数据目录与密钥文件 0600 |
| 日志泄露 | 日志已脱敏；`secret` 包不打印任何密钥 |
| 界面泄露 | API 永不返回明文 |
| 备份文件 | 含密文与 DPAPI blob，拷到别的机器同样解不开 |

**防不了「以当前用户身份运行的恶意程序」**——它能读 DPAPI、能读进程内存。
单用户本机场景下，这条防线只能防「别人翻你的文件」，防不了「你的机器被入侵」。

## 后果

- 删 Provider 时同步清理密钥（`SaveProviders` 里做）
- 换 Windows 用户 / 换机器后，已存密钥不可用，需要走重置入口重填
- 备份天然安全，但恢复后只能在原用户下使用
- `config.Provider.Validate` 不再强制 `api_key_env`——否则界面上
  「先建 Provider 再填密钥」这条路走不通
