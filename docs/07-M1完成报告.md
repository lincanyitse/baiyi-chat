## 交付内容

### Agent 运行时（`internal/agent`）

八态显式状态机：

```
Ingest → Assemble → Infer → Decide → Execute → Refill → (回到 Infer)
                                     ↘ Finalize → Done
```

- **步数/墙钟/工具数三重预算**，超限强制收敛而非无限循环
- **并行工具执行**：结果按下标写预分配切片，天然保持 `tool_use` 原始顺序
- **panic 隔离**：单个工具崩溃只影响自己，且**仍写入幂等缓存**
- **续跑**：transcript 是 append-only 步骤日志，恢复是纯函数——不依赖状态机快照
- **降级链**：首选 Provider 失败且错误可降级时，自动尝试后续候选

### 工具协议（`internal/tool`）

```go
type Tool interface {
    Spec() Spec
    Execute(ctx, in json.RawMessage, ec *ExecContext) (Result, error)
}
```

- 三级风险（read / write / dangerous）驱动审批策略
- 结果按 token 与字节双上限截断，完整内容落 `tool_output_store` 并返回句柄
- 内置工具：`time_now`、`tool_output_read`、`ask_user`、`load_skill`
- MCP 工具与内置工具走同一接口，运行时无需感知来源

### 上下文工程（`internal/contextx`）

八段分层，按稳定性排序：

| 段 | 内容 | 特性 |
| --- | --- | --- |
| 1 身份规则 | 人格与约束 | **稳定前缀** |
| 2 工具技能目录 | Schema + L0 列表 | **稳定前缀** |
| 3 画像卡 | 用户偏好摘要 | **稳定前缀** |
| 4 情节召回 | 相关历史事件 | 可裁剪 |
| 5 RAG | 检索片段 | 弹性池，优先裁剪 |
| 6 对话历史 | 消息数组 | 可摘要/丢弃 |
| 7 当前输入 | 本轮用户输入 | **永不裁剪** |
| 8 便签 | 时间、待办 | 易变 |

**降级顺序严格固定**：丢低分 RAG → 压画像卡 → 工具结果换句柄 → 滚动摘要 → 丢最老轮次 → 明确报错。

### 技能（`internal/skill`）

- `skills/<name>/SKILL.md` + YAML frontmatter，放进目录即生效
- 三级渐进披露：L0 名字+一句话常驻 → L1 正文按需 → L2 参考资料再按需
- **两种触发**：模型自主判断调 `load_skill`，或命中 `triggers` 关键词时确定性激活
- 目录指纹用**内容哈希**而非 mtime（Windows 上同秒改写 mtime 不可靠）

### MCP（`internal/mcp`）

- stdio（`CommandTransport` + Windows `cmd /c` 包装）与 Streamable HTTP
- 工具名映射 `mcp__<alias>__<tool>`，超限时退化为确定性短名
- 白名单过滤、单 server 故障隔离
- MCP 工具描述与返回内容均标记为**不可信外部输入**

## 实施中发现的真实缺陷

按严重程度排序。每一个都会在生产环境咬人。

| # | 缺陷 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | **迁移不幂等**：`ALTER TABLE ADD COLUMN` 不检查列是否存在 | 迁移中途崩溃后重试会因重复列失败，数据库卡死 | 执行前查 `PRAGMA table_info` |
| 2 | **段级配额被总预算掩盖**：RAG 用了 2110 token 而配额仅 515，因总量未超预算而不裁剪 | 配额形同虚设，单个弹性段可无限膨胀 | 降级停止条件改为「总量与各段配额都达标」 |
| 3 | **网络错误归为 unknown**：`AsError` 未识别连接失败 | 降级链完全不触发，Provider 挂了就整轮失败 | 按错误文本宽松匹配（Windows/Linux 措辞不同） |
| 4 | **工具 panic 漏写幂等缓存** | 续跑时同一调用被重复执行 | recover 分支也走 `recordToolResult` |
| 5 | **本轮工具往返未计入快照** | 快照显示「历史 4 token」，模型实际收到了完整往返，诊断失真 | 引入 `LiveTurns`，如实计入 |
| 6 | **污点追踪失效**：`tainted()` 沦为死代码 | 「接触外部内容后永久允许不再可信」的安全语义丢失 | 污染时取消已授权豁免 |
| 7 | **`ask_user` 拿不到 Approver** | 工具永远无法工作 | `ExecContext.Approver` 正确传入 |
| 8 | **控制台日志走 stdout** | 打断 REPL 对话输出，无法管道处理 | 改为 stderr |
| 9 | **SSE 注释行被当成事件** | 纯注释流在末尾返回空事件，`ping` 保活被误判 | 注释判断提前到 `started` 之前 |
| 10 | **`SkillLines` 断链**（收尾审查发现）：session 填了、agent 声明了，但 agent 构造 `contextx.Input` 时从未转发 | 技能目录**从未进入系统提示**，模型看不到技能清单，只能靠 trigger 关键词或瞎猜。三处注释都宣称「进入稳定前缀段」 | 补上转发；实测工具目录从 166 → 185 token |
| 11 | **续跑重复落库用户消息**（文档核对时发现）：`ResumeTurn` 复用 `Ask`，而 `Ask` 无条件追加用户消息 | 每次 `/resume` 都会在 transcript 里多出一条相同输入，历史被污染 | `AskOptions.ResumeTurnID` 标识续跑，跳过落库并复用原 turn |
| 12 | **每次启动新建会话**（文档核对时发现）：REPL 的 `ensureSession` 无条件 `CreateSession` | 会话列表无限膨胀，用户找不到上次对话 | 优先复用最近一个有消息的会话 |

## 收尾审查（`/simplify` 四角度）

M1 完成后做了一轮复用 / 简化 / 效率 / 层次审查，主要清理：

| 类别 | 问题 | 处置 |
| --- | --- | --- |
| **断链** | `SkillLines` 三处接线但中途丢弃（见缺陷 #10） | 修复（唯一的功能性缺陷） |
| **双真源** | 历史配额 35% 在 `contextx` 与 `session` 各写一份 | 新增 `contextx.HistoryQuota`，唯一真源 |
| **双真源** | `keepRecent` 两处硬编码 16 | 统一为 `keepRecentTurns` |
| **重复** | `countTokens` 两份实现 | 导出 `contextx.CountTokens` |
| **性能 O(n²)** | `dropLowestRAG` 每丢一个片段就全量重渲染 | 预计算 + 增量累减 |
| **性能** | 历史哈希用 `fmt.Sprintf("%v", history)` 展开整段 | 遍历角色与文本块 |
| **性能** | `toolSpecs` 每步构造两次（MCP 每次 `json.Marshal` schema） | turnState 初始化时缓存 |
| **死代码** | `Spec.Idempotent` / `Spec.MaxConc` / `Result.Summary` / `TaintState.Sources` / `Client.Healthy` / `registry.Fallbackable` / `MarshalSummaryState` / `Segment.BlobHash` / `usedModel` / `lastSnapshot` | 全部删除（约 120 行） |

**刻意保留的**（记录理由，避免下次重复讨论）：

| 项 | 保留原因 |
| --- | --- |
| `storeAdapter` / `snapshotSink` 留在 session | 移进 `store/sqlite` 会引入 `store → agent` 的新依赖；M2 加表时再统一定位 |
| `llmSummarizer` 未抽公共「内部任务执行器」 | 目前只有一个使用者；M2 的记忆抽取与查询改写会按真实需求定型 |
| `Compressor` 未下沉到 contextx | 它需要 `Summarizer`（依赖 Provider），下沉会让 `contextx` 不再只依赖 `llm` 纯数据 |
| `mapToolChoice` 两份 | 各 5 行、同 PR 内改动，抽公共反而增加跨包跳转 |
