F 阶段是 M3.2 的最后两块：

| 项 | 交付 |

| 局部口令 | Argon2id + HttpOnly Cookie 会话，首次设置/登录/改口令/重置 |

## 本地口令

### 威胁模型

场景是**单用户、本机运行**。要防的不是远程攻击者，而是「同一台机器上的
其他人打开浏览器就能看到我的全部对话」。所以这是一道本机隔离措施，
不是账号体系——没有用户表、没有权限角色、没有多租户。

这个定位决定了几件事：

- 只存一条记录（`web_auth` 表的 `id = 'default'`）
- 不做登录限流：本机暴力爆破没有意义，加限流只是给自己添堵
- 不做 CSRF token：`SameSite=Strict` 已经阻断跨站携带
- token 不落库：重启即需重新登录，可接受

### Argon2id

参数 `m=64MiB, t=1, p=4`，单次验证约 50–100ms。存 PHC 格式：

```
$argon2id$v=19$m=65536,t=1,p=4$<salt>$<hash>
```

参数随哈希一起存，将来调参能兼容旧记录。比对用
`subtle.ConstantTimeCompare`，避免计时侧信道。

口令强度只查长度（≥8 字符），不设复杂度规则。大小写混排那类规则实际
收益很低，只会逼出 `Password1!`。

### 会话

登录成功签发 32 字节随机 token，存内存 map + `HttpOnly; SameSite=Strict`
Cookie，有效期 7 天。同时支持 `Authorization: Bearer`——脚本和 curl
用 Header 比管 Cookie 方便。

**改口令会让所有已登录会话失效**，包括当前这个（随后重新签发）。

### 中间件的关键陷阱

第一版把「是否启用口令」判断放在 `New()` 里构造中间件时做：

```go
func (s *Server) requireAuth(next http.Handler) http.Handler {
    enabled, _ := s.opts.Auth.Enabled()   // ← 启动时
    if !enabled { return next }            // ← 永久放行
    ...
}
```

但口令是**运行期**通过 `/api/auth/setup` 设置的，服务启动那一刻还没有。
结果就是：设置口令后接口仍然完全敞开。实测时发现——设置了口令，
无 Cookie 访问 `/api/sessions` 依然 200。

修法是把判断移进 handler 内部，每次请求重新查。补了
`TestAuthEnabledAfterStartup` 锁住这个行为。

### 忘记口令的出口

`baiyi reset-password` 直接清空 `web_auth` 表。这是唯一的自救路径：
不需要先登录，只要能在本机执行命令。

## 配置写回

### 为什么不整份序列化

`toml.Marshal(整个 Config)` 有两个问题：

1. **注释全丢**。用户的配置文件里有大量说明性注释（`config.example.toml`
   本身就是一份文档），重新序列化会把它们全部抹掉。
2. **字段漏了就静默丢失**。`Config` 有十几个字段，`Marshal` 时任何一个
   忘记处理，用户的配置就被悄悄改掉了。

### 外科手术式替换

`config.SaveProviders` 只做三件事：

1. 按行扫描原文件，删掉所有 `[providers.*]` 与 `[route.*]` 段
2. 把新配置渲染成 TOML 文本，插回第一个被删的位置
3. 交给解析器自检语法，通过后写临时文件再 `rename`

其余字节**原样保留**——注释、空行、手写排版都不动。

段头识别按行前缀匹配（`[providers.` / `[route.`），不用正则：TOML 的
字符串值里可能出现类似文本，按行扫描更安全。

渲染时字段顺序固定、Provider 与模型名排序，保证同样的配置每次写出
同样的文本，`git diff` 才有意义。

### 热重载

保存后 `registry.Build(newCfg)` 重建注册表，再 `Service.SetRegistry()`
替换。**进行中的轮次不受影响**：`AskWith` 在开头就把 Provider 取出来
存进 `agent.TurnInput`，手里握着旧实例直到这一轮跑完。

顺序是先写文件、后重建。反过来的话，新 Registry 可能基于一份没落盘的
配置，重启后又变回去。重建失败时文件已经落盘——这时代码返回错误但
**不换掉旧 Registry**，运行中的服务还能继续用，用户改回去再保存即可。

### 只允许改 Provider

`Config` 里的其他字段（数据目录、日志、会话预算）改了对运行中的进程
没有意义：它们要么在启动时就固化了，要么需要重建整个装配。做成
「保存后立即生效」反而是误导，所以写回只覆盖这两段。

## 前端

### 登录门

`App.svelte` 在渲染主界面前先查 `/api/auth/status`：

- `auth === null`（还在查）→ 显示空白，避免闪一下登录页
- `enabled && !logged_in` → 显示 `LoginGate`
- 其余 → 正常界面

会话列表的加载也依赖这个状态：未登录时拉列表会 401，白白闪一条错误。

### 管理面板

「模型服务」从只读展示改成可编辑：Provider 增删、类型下拉、URL、
密钥环境变量名、超时、模型能力勾选、任务路由。用可编辑副本，点保存
才提交。

「安全」页做设置/修改口令与状态展示。

## 发现的真实缺陷

**1. 认证中间件在构造时判断「是否启用」，导致口令设置后仍然全开放。**
见上文。这是实测发现的——单元测试用「先设口令再建服务」的顺序，
恰好绕过了这个问题。

**2. `ProviderDTO` 的 BaseURL 脱敏会毁掉配置。**
早先为了「不暴露内网拓扑」只返回 `scheme://host`。改成可编辑后，
编辑界面拿到的是截断的 URL，保存就把 `/v1` 路径丢了。改为返回完整值——
这个接口本来就需要登录才能访问。

**3. 保存后的响应还是旧配置。**
handler 用 `s.opts.Providers`（启动快照）渲染响应，没有随保存更新。
加了带读写锁的 `cfgProviders`/`cfgRoutes` 字段，保存成功后刷新。

**4. `rg` 把 `//` 注释连到下一行。**
`applyToolPolicy 按配置收窄工具集。//` —— sed 替换时误删了换行。
这是编辑事故，不是设计问题。

## 后续：模型列表查询

Provider 编辑界面原本要手抄模型 ID，抄错只能等运行时 404。
`llm.ModelLister` 接口与 `Registry.ListModels` 早就存在，只是没接出来。

| 层 | 改动 |
| --- | --- |
| `channel/web` | `GET /api/providers/{name}/models` |
| 前端 | 模型 ID 输入框挂 `<datalist>`，旁边加「获取模型列表」按钮 |

**刻意不自动写入配置**：接口返回的只有 ID，上下文窗口、是否支持工具、
是否计费这些能力声明只有用户知道。自动补全会把猜测当事实写进配置，
比手抄更容易出错。列表只用于做输入候选。

只有 `openai-compat` 与 `responses` 适配器实现了 `ModelLister`；
`anthropic` 的原生接口没有 `/models`，调用会返回「不支持列出模型」。

## 代码审查修复（/simplify）

对 F 阶段代码做了四视角审查（复用/简化/效率/层次），修掉的实质问题：

**数据丢失 bug**：`ModelDTO` 缺 `prefix_cache` / `price_cached` /
`strict_schema` 三个字段。GET 不返回它们 → 界面读不到 →
保存时按零值写回 → 用户在配置文件里手写的值被静默清零。
这已经超出「重复代码」的范畴，是真 bug。修法：补全字段，
并让 `ProviderInput` 直接复用 `ModelDTO`，消除两份镜像结构体。

**两次多余的 Argon2id**：`Auth.Setup` 刚哈希完口令，handler 又调
`Login` 验证同一口令；`Change` 更是一次请求跑三次。Argon2id 单次
50–100ms，setup 因此慢了一倍。修法：`Setup`/`Change` 直接返回
session token，不再让调用方二次验证。实测 setup 从 ~150ms 降到 73ms。

**每请求一次库查询**：`Enabled()` 被中间件在每个请求上调用。
加 `atomic.Int32` 缓存，初值未知时查库，`Setup`/`Change`/`Reset`
三处写路径是完备的失效点。

**会话时长两处硬编码**：`Auth.ttl` 与 Cookie `MaxAge` 是同一个业务
常量。修法：提取 `sessionTTL` 常量。

**死代码**：`AuthEnabled`、`ReloadConfig`、`ErrUnsupported`、
`LoginGate` 的 setup 分支、AdminPanel 里旧版 Provider 卡片的样式。

**其余**：
- `Auth == nil` 守卫四连抄 → `authOrNotFound`
- `authReq` 与 `testEnv.do` 重复 → 给 `do` 加可变 Cookie 参数
- `quote()` 每次走 `toml.Marshal` 反射 → `strconv.Quote`
- 前端口令校验在两处各写一份 → `lib/password.js`
- `ProviderEditor` 的 `current`/`draft`/`editedRoutes` 三份状态
  → 只留一份草稿，保存后由 `{#key}` 重挂载重置
- `Valid()` 顺带清理过期会话，不再依赖「下次登录」这个偶然事件

**跳过**：`Auth` 放在 channel 层（审查建议抽到 `internal/auth`）。
它是本机单用户的口令 + 会话表，与 HTTP Cookie 强绑定；抽出去要么
在 auth 包里重新引入 HTTP 概念，要么把 token 表与口令存储拆成两半。
当前分层检查通过，改动收益不抵成本。`Enabled()` 的 fail-open
（DB 故障时放行）同理保留——本机场景下 DB 挂了更严重的问题已经发生，
此时拦截所有请求只会让诊断更困难。
