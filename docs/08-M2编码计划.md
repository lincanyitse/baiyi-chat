## Context

M1 让白泽能调用工具、多步推理，但它**不记得你**，也**读不懂你的资料**——每次对话都从零开始，问它「我上次说的那个项目」它一无所知。

M2 补上这两块：**记忆**（四类、跨会话、可撤销）与 **RAG**（接入文档、混合检索、可点击引用）。

11 项交付物估计 15–20 人日，拆成 **M2.1（RAG）→ M2.2（记忆）**：先做 RAG，因为效果直观可验（丢文档进去，问它答得出来且给引用）；记忆的设计取舍更多，放后面更从容。

### 已确认的决策

| 维度 | 决策 | 理由 |
| --- | --- | --- |
| 拆分 | M2.1 RAG → M2.2 记忆 | RAG 效果可直观验证，先建立信心 |
| 嵌入服务 | **抽象接口**，三种后端：OpenAI 兼容 / Ollama / 自定义 HTTP | 当前网关无 embedding 模型，不能被单一服务商绑死 |
| 重排 | 一并接外部 rerank，不可用时退化为 RRF | 架构已设计好降级路径 |
| 向量存储 | SQLite BLOB + 进程内 int8 量化 | 个人规模够用，不引入外部向量库 |

### 必须先修的三个 M1 遗留缺陷（已核实）

| # | 缺陷 | 现状 | 影响 |
| --- | --- | --- | --- |
| 1 | **`joinSystem` 把段 4/5/8 拼进 system** | `assembler.go` 只跳过 `SegHistory`/`SegInput` | M1 时段 4/5/8 是空的所以没暴露。M2 一填记忆/RAG，**每轮变化的内容会让 Anthropic 前缀缓存从头失效**，成本翻倍 |
| 2 | **`approved(name, risk)` 忽略 risk 参数** | 参数收了不用 | 危险工具一旦在本会话被批准一次，后续永久跳过审批，违背 FR-TOL-002「危险操作永远确认」 |
| 3 | **`TurnInput` 缺 `Episodes`/`RAGChunks`** | 只有 `ProfileCard` | M1 已发生过 `SkillLines` 接线断链的同类问题，必须配「三段接线」测试 |

**缺陷 1 的修法**（影响面最大，先说清）：

```
现在：system = 段1 + 段2 + 段3 + 段4 + 段5 + 段8   ← 段4/5/8 每轮变
改成：system = 段1 + 段2 + 段3                      ← 稳定前缀
      段4/5/8 作为当前用户消息的首个文本块注入       ← 追加区
```

配一条测试：仅 RAG 或情节变化时，`PrefixHash` 必须不变。

### 边界规则

| 规则 | 说明 |
| --- | --- |
| `memory` 与 `rag` **永不 import 对方** | 嵌入能力由 `internal/embed` 提供，两者各自消费 |
| `embed` 只依赖 `llm` + stdlib | 记账通过 `embed.Meter` 回调（接口开在 embed，bootstrap 用 `cost.Ledger` 实现），避免 `embed → cost` |
| `jobs` 只认 `Handler` 接口 | `Handler{Kind, Handle(ctx, Job) error}`，不认具体业务；六个 handler 由 bootstrap 注册 |
| `contextx` 保持纯数据 | 由 session 负责填充 `ProfileCard`/`Episodes`/`RAGChunks` |

### 四个关键边界决策

**1. 嵌入接口放 `internal/embed`，不放 `rag`。**

架构纲要 §2.4 原本写的是 `rag.Embedder`。但记忆的情节向量化也要用嵌入，放 rag 会强制 `memory → rag`，把解析、切分、FTS 全拖进记忆的依赖闭包。

`embed` 是中立能力包，`memory` 与 `rag` 各自消费，共用限流与记账底座。**记 ADR-0015**。

**2. 向量共用一张 `embeddings` 表，元数据分表。**

`owner_kind('chunk'|'episode') + owner_id + model + dim`，文本与偏移仍在 `chunks`/`episodes`。

理由：重建逻辑、量化、扫描、幂等键四份代码只写一次。代价是多一个枚举字段，值得。

**3. RAG 不在热路径预取。**

查询嵌入是网络调用（30–100ms），会击穿 NFR-PERF-001（本地开销 <100ms）。

RAG 由模型调 `rag_search` 工具，结果以 `tool_result` 回填——同 `load_skill` 的先例，不污染稳定前缀。

**4. 画像卡不做每轮 LLM 重写。**

措辞每轮变化会让稳定前缀抖动，缓存全废。改为：`profile_card` 表存**渲染好的行**，只在 facts 变更时重算（`profile_state.generation` 比对）。

## 关键设计决策

### 1. 嵌入后端：一个接口，三种实现

```go
type Embedder interface {
    Embed(ctx context.Context, model string, texts []string) ([][]float32, Usage, error)
    Dimensions(model string) int
}

type Reranker interface {
    Rerank(ctx context.Context, model, query string, docs []string) ([]float32, Usage, error)
}
```

配置驱动：

```toml
[embed]
kind        = "openai"      # openai | ollama | custom | fake
base_url    = ""
api_key_env = ""
model       = "bge-m3"
batch_size  = 64

[rerank]
kind        = "openai"
model       = "bge-reranker-v2"
```

`kind = "fake"` 用于开发与降级：确定性哈希伪向量，链路完整但语义无效，**日志明确标注「fake 模式，检索结果无语义意义」**。

### 2. 切分：解析期就产出带类型的块

`rag.Parser` 输出 `Doc{Sections[]{HeadingPath, Kind, Text, Page}}`，`Kind ∈ {heading, para, table, code}`。

| 规则 | 说明 |
| --- | --- |
| 表格与代码是**原子块** | 围栏代码块与 Markdown/HTML 表整块识别，≤800 token 不切 |
| 超长原子块按行切 | 重复表头/围栏，保证每块可独立理解 |
| 其余按段落打包 | 400–800 token，重叠 10–15% |
| 重叠只在段落边界 | **不按字节切**，否则中文断句 |
| 嵌入文本 | `heading_path + "\n" + text` |
| 存储与展示 | 仍用 `text`，同时记 `start_off/end_off/page` 供引用跳转 |

### 3. FTS5 bigram：ASCII 整词保留

关键细节：**中文切二元组，ASCII/数字整词保留**。否则 `RAG` 会变成 `RA AG` 造成误命中。

```go
// 「白泽 RAG 助手」→ "白泽 泽R RAG AG 助手"（ASCII 整词保留）
```

查询必须包 phrase 并转义 `" * ( ) : ^ -`：

```sql
WHERE text_bigram MATCH '"白泽 泽助 助手"'
```

用 `content=''` + `contentless_delete=1` 省一半索引体积。

**迁移执行器约束**：`splitSQL` 按行尾 `;` 切分，FTS5 建表语句必须写成单行且不以分号结尾。

### 4. 混合检索：RRF + 可选重排

```
向量 top-30 + 关键词 top-30
  → RRF(k=60): score = Σ 1/(60 + rank)
  → 去重取 top-50
  → 重排（可选）→ 保留 8-12 条
```

重排不可用时直接用 RRF 分数，工具结果首行注明「重排不可用，已按融合分排序」，**不报错**。

### 5. 向量存储：三档策略

| 规模 | 策略 | 内存 |
| --- | --- | --- |
| < 15 万行 | 进程内 int8 矩阵，按需加载，空闲 10 分钟释放 | 100k × 1024B ≈ 100MB |
| 15 万+ | SQLite 流式扫描 + 容量 K 的堆 | O(K) |
| 更大 | 接外部向量库（OQ-008） | — |

**原始 f32 只用于写入与 top-50 精排，永不整体 materialize**。

估算依据：20 万 × 1024 维 × 4B = 819MB，全载入内存不可接受；量化到 int8 后 100k 行约 100MB，可接受。

### 6. 记忆写入：规则优先，不上小模型

热路径零额外调用：

```
抽取 → 候选
  ↓
subject_key/predicate_key 归一化（小写、全角转半角、去空白）后精确匹配
  ↓
value 精确或 bigram Jaccard ≥ 0.9  → duplicate（加确认次数、提置信度，不新增行）
同键不同值 + 新来源优先级严格更高  → update（旧行写 valid_to，新行 active）
同键不同值但优先级不够            → contradict（新行 disputed，旧行保持 active，绝不覆盖）
不同键                            → unrelated 直接插入
```

来源优先级：`explicit 1.0 > turn 0.8 > session_end 0.7 > external 0.3`。

**「宁可漏记，不可错记」**：向量近邻只用于 `memory_search` 与后续复核，**不进自动写入路径**。

### 7. 外部内容不进画像卡：三层强制

| 层 | 措施 |
| --- | --- |
| 落库 | `turns.trust='external'` 标记污点轮 |
| 抽取 | SQL 只取 `trust <> 'external'` 的轮次，物理上拿不到 |
| 查询 | 画像卡 SQL 硬过滤 `source_type IN ('explicit','turn','session_end','imported')` |

三层任一失效都不至于污染画像。

### 8. 召回：预召回纯 SQL，向量留给工具

| 通道 | 内容 | 延迟 |
| --- | --- | --- |
| 每轮预召回 | 画像卡（≤300 token）+ 条件触发的 top-3 情节 | < 10ms（纯 SQL） |
| 主动检索 | `memory_search` 工具，可用向量 | 按需 |

**热路径不做查询嵌入**——那会引入 30–100ms 网络延迟。

情节召回的「时间/指代线索」用关键词与正则：`上次|之前|上回|那天|当时|继续|那个|这个项目|以前|后来` + 日期模式。

排序用 SQL：实体命中数 × 2 + 摘要 bigram 命中 + 时间近因。

注入优先级：`score = importance × decay × (1 + 0.15·ln(1+access)) × trust`

- 情节 `decay = 2^(-age_days/90)`（半衰期 90 天）
- 语义事实 `decay = 1`（内容不衰减，只降排序）
- 阈值 0.25，低于阈值归档但**不删除**
- `source_type='explicit'` 强制 `importance=1, decay=1`（FR-MEM-011：用户显式记忆永不自动遗忘）

### 9. pathjail：Windows 专项防护

`internal/infra/pathjail`（L0，仅 stdlib）。

**拒绝清单**：UNC（`\\`）、设备路径（`\\?\`、`\\.\`）、驱动器相对（`C:foo`）、ADS（`file.txt:stream`）、保留设备名（CON/PRN/AUX/NUL/COM1-9/LPT1-9）、结尾点/空格、控制字符。

**流程**：`Abs+Clean` → 对 root 与目标各 `EvalSymlinks` → **大小写不敏感**前缀比较 → 通过后才加 `\\?\` 长路径前缀。

写入后 `os.SameFile` 复核缓解 TOCTOU，残余风险写进 ADR。

牢笼根默认 `<data>/workspace`，硬拒 `<data>/baiyi.db`、`secrets.dat`、`backups/`。

### 10. 技能脚本：窄工具，不是通用 shell

`skill_run` 工具：`Risk=Dangerous`、超时 60s、输入 `{skill, script, args[]}`。

| 约束 | 说明 |
| --- | --- |
| 路径 | 限定在 `<skills>/<name>/scripts/`，经 pathjail |
| 扩展名白名单 | `.ps1/.cmd/.bat/.sh/.js` |
| 解释器 | 从**配置白名单**解析，绝不按模型输入查 PATH |
| 环境变量 | 白名单化，剥离 `*_API_KEY`、`ANTHROPIC_*`、`OPENAI_*` |
| 输出 | 经 `tool.TruncateResult` + `OutputStore` 句柄化 |

**同时修 `needsApproval`**：`Risk==Dangerous` 时忽略会话级/永久授权（缺陷 2）。

### 关键索引

```sql
-- jobs：去重靠部分唯一索引
CREATE UNIQUE INDEX idx_jobs_dedupe ON jobs(kind, dedupe_key)
  WHERE dedupe_key <> '' AND status IN ('pending','running');

-- facts：当前真值唯一（历史版本 status 不是 active）
CREATE UNIQUE INDEX idx_facts_active ON facts(subject_key, predicate_key)
  WHERE status = 'active' AND deleted_at IS NULL;

-- embeddings：主键含 model，新旧模型共存，重建是纯加法
PRIMARY KEY (owner_kind, owner_id, model)
```

### 导出格式

目录形式：

```
manifest.json          版本、schema_version、计数、embed_model
sessions.jsonl
memory.jsonl           facts 全版本 + events
```

## 风险与预案

| 风险 | 早期信号 | 预案 |
| --- | --- | --- |
| **动态段破坏前缀缓存** | 纯对话 3 轮 `PrefixHash` 变化、缓存命中率骤降 | system 固定为段 1–3；段 4/5/8 进当前消息；画像卡只在 facts 变更时重算 |
| **记忆污染** | facts 周增速异常、`disputed` 占比高、画像卡出现 external（应为 0） | 一键关异步抽取；`memory_events` 批量回滚；SQL 硬过滤 |
| **检索质量/切分失控** | 30 题人工评测召回 <80%、平均 chunk >900 token、引用偏移错位 | 切分退化为段落定长；rerank 默认关；提高 FTS 权重 |
| **SQLite 单连接争抢** | 对话 p95 抖动、`busy_timeout` 命中、jobs 积压 | jobs 限并发 1 且只看空闲窗口；只读检索走第二条只读连接；向量矩阵驻内存减少扫描 |
| **嵌入成本失控** | `purpose=embed` 日成本异常、重建进度停滞 | 重建限速 + 日预算上限；默认夜间执行，可暂停 |

### 与计划的偏离

**1. FTS5 用普通表而非 contentless。**
计划写的是 `content=''` + `contentless_delete=1`。实测发现 contentless 表的
`chunk_id` 是 UNINDEXED 列，`DELETE ... WHERE chunk_id = ?` 永远匹配不到行——
删除文档时 FTS 行会留下，检索命中已删除的 chunk 再查库得到空。
改为普通 FTS5 表：索引体积大约翻倍，但删除语义正确。个人规模下这点体积不值得用正确性换。

**2. `embed` 不依赖 `config`。**
最初写了 `embed.FromConfig(config.EmbedConfig)`，随即发现这会让 `config`
（koanf、文件系统、环境变量）进入每个消费嵌入的包的依赖闭包。
改为 `embed.Settings` 扁平结构，翻译放在 `bootstrap`。

**3. 查询二元组需要两档匹配。**
中文切二元组时，跨词边界会切出原文不存在的组合——「白泽助理」切出
「泽助」，严格 AND 匹配零命中。改为严格式（AND）优先、零命中退宽松式（OR）。
这是二元组方案的固有代价，不是实现缺陷。

**4. 切分必须跨 Section 打包。**
Markdown 解析器把每个段落产成一个 Section。若逐个 Section 独立切分，
每段各自成块，打包与重叠机制完全失效（实测 10 段文档产出 10 个 chunk，
目标 80 token 时本该是 3-4 个）。改为先按 `heading_path` 归组、组内打包。

**5. 字符偏移由解析器给出，不在切分器推算。**
`Section` 增加 `CharOffset` 字段。切分器推算偏移时要跨过标题行与空行，
必然偏小，用户点引用会跳到错误段落。Markdown 与 Text 解析器精确填写；
HTML 因结构被重排（去掉导航/页脚）填 0，引用只能定位到 chunk。

## 「是否保留旧向量」的结论

**保留。** 用户开工前提出的这个问题，实测答案如下。

`embeddings` 表主键是 `(owner_kind, owner_id, model)`，因此：

- 换模型后旧向量原地保留，新模型向量与之并存，互不覆盖
- 切回旧模型时 `RebuildEmbeddings` 查 `ChunkIDsWithoutVector` 得到 0 条，
  **零次嵌入调用**即恢复检索能力
- 不同维度的向量共存在同一张表里不冲突（列是 BLOB，维度记在 `dim` 列）

代价是空间：1024 维 int8 每条约 1KB，10 万片段即 100MB/模型。
个人规模下这个代价远低于「切回旧模型要重算两小时」。

三个测试锁定该行为：
- `TestModelSwitchKeepsOldVectors`：换模型后旧向量数不变，切回零重算
- `TestModelSwitchDimensionIsolation`：64 维与 1024 维并存不串味
- `TestSwitchBackFasterThanRecompute`：已建索引再重建，嵌入调用次数不变

唯一会删旧向量的入口是 `DeleteVectorsByModel(keep)`，它**不被任何自动流程调用**，
只留给未来「清理磁盘」这类显式操作。
