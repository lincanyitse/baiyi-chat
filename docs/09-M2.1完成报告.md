## 关键设计决策

### 1. 嵌入接口独立成包，不放 rag

`memory` 的情节向量化也要用嵌入。若接口开在 `rag`，就会强制 `memory → rag`，
把解析、切分、FTS 全拖进记忆的依赖闭包。`embed` 是中立能力包，两者各自消费。

`embed` 只依赖 `llm` 与标准库；配置翻译放在 `bootstrap`——一旦它 import `config`，
koanf、文件系统、环境变量就会进入每个消费嵌入的包的依赖闭包。

### 2. 向量共用一张表，主键含模型

`embeddings(owner_kind, owner_id, model)`。所以：

- 换模型后旧向量原地保留，新旧并存
- 切回旧模型时 `ChunkIDsWithoutVector` 返回 0 条，**零次嵌入调用**即恢复
- 不同维度共存不冲突（BLOB + `dim` 列）

代价是空间：1024 维 int8 每条约 1KB，10 万片段 100MB/模型。个人规模下
这远低于「切回旧模型要重算两小时」。

唯一删旧向量的入口 `DeleteVectorsByModel(keep)` **不被任何自动流程调用**。

### 3. 切分跨 Section 打包

Markdown 解析器把每个段落产成一个 `Section`。若逐个 Section 独立切分，
每段各自成块，打包与重叠机制完全失效（实测 10 段文档产出 10 个 chunk，
目标 80 token 时本该是 3–4 个）。

改为先按 `heading_path` 归组、组内打包；代码与表格作为原子块独立成组。

### 4. 字符偏移由解析器给出

`Section.CharOffset` 由解析器填精确值。切分器推算偏移要跨过标题行与空行，
必然偏小，用户点引用会跳到错误段落。

Markdown 与 Text 解析器精确填写（逐行累计）；HTML 因结构被重排
（去掉导航/页脚）填 0，引用只能定位到 chunk。

### 5. FTS5 用普通表而非 contentless

计划里写的是 `content=''` + `contentless_delete=1`。实测发现 contentless 表的
`chunk_id` 是 UNINDEXED 列，`DELETE ... WHERE chunk_id = ?` 永远匹配不到行——
删除文档时 FTS 行会留下，检索命中已删除的 chunk 再查库得到空。

改为普通 FTS5 表：索引体积大约翻倍（因为要把 `chunk_id` 与影子列都存一份），
但删除语义正确。个人规模下这点体积不值得用正确性换。

### 6. 查询二元组用两档匹配

中文切二元组时，跨词边界会切出原文不存在的组合——「白泽助理」切出「泽助」，
严格 AND 匹配零命中。

改为严格式（全部二元组 AND）优先、零命中退宽松式（OR）。这是二元组方案的
固有代价，不是实现缺陷。

## 发现的真实缺陷（8 个）

### 修复前三个 M1 遗留

| # | 缺陷 | 处理 |
| --- | --- | --- |
| 1 | `joinSystem` 把段 4/5/8 拼进 system，破坏前缀缓存 | 已在 M1 收尾修复，本次补测试锁定 |
| 2 | `approved(name, risk)` 忽略 risk，危险工具被永久放行 | 已修（危险工具永远审批） |
| 3 | `TurnInput` 缺 `Episodes`/`RAGChunks` | **本次核实确实断链**，已补 |

第 3 个是计划中预判的「接线断链」，与 M1 的 `SkillLines` 同类。
新增 `TestTurnInputReachesAssembler` 断言五段都真的到达 `contextx.Input`。

### 本次新发现

**4. `llm.ParseHTTPError` 消费响应体。**
先读 `raw` 再调它会得到空错误消息。修复：非 2xx 时先调它。

**5. 自定义后端剥引号破坏文本。**
用 `strings.Trim(s, "\"")` 从 JSON 转义结果里剥引号，会贪婪剥掉文本自身的
结尾引号，产出非法 JSON。改为解析模板后递归替换字符串值，转义交给
`encoding/json`。

**6. contentless FTS5 无法按值删除。**
见「关键设计决策」第 5 条。

**7. 切分器逐 Section 处理，打包与重叠完全失效。**
见「关键设计决策」第 3 条。

**8. 中文二元组跨词切出伪词，严格匹配零命中。**
见「关键设计决策」第 6 条。

### 联调阶段（跑真实应用才暴露）

**9. `App.Close()` 取消 ctx，正在跑的嵌入任务半途失败。**
用户刚 `/kb add` 的文档永远补不上向量，任务状态还是 `failed`，看起来像配置错了。

修复：`Stop()` 只置停止标记并等 worker 自然退出，不取消 ctx；
另加 `Cancel()` 供必须立刻退出时使用。`stopping` 从 channel 改为
`atomic.Bool` + `sync.Once`。

**10. `SetDocumentEmbedModel` 顺带写 `char_count` 且传 0。**
文档列表里字数全部显示为 0。一个函数干两件事，其中一件被用错了。
修复：只改模型字段。

**11. Ollama 超长输入导致整篇失败。**
Ollama 嵌入上下文 4096 token，超长返回 500 且带
`"the input length exceeds the context length"`。切分器的代码块与表格是原子块，
超长时整块保留，必然触发。

修复：客户端按 3000 字截断；服务端此类错误归为新增的 `ErrUnsupportedInput`，
不参与重试。

**12. 不可重试的错误被重试。**
原 `isRetryable` 只要 `ErrUnavailable` 就重试。Ollama 用 500 表示输入超长，
于是每条坏输入重试 3 次 × 指数退避（7s）。一张大表格就能把索引拖慢几十秒。

修复：输入类错误（`ErrUnsupportedInput`）与连接失败（`ErrUnreachable`）
都不重试。

**13. `EmbedDocument` 无条件重算全部片段。**
重复调用（`/kb rebuild`、任务重试、文档更新）会重新嵌入已有片段。
Ollama CPU 上 1–2 秒/条，100 片段的文档白烧两分钟。

修复：先查 `VectorizedChunkIDs`，只补缺失的；全部就绪时零调用。

## 性能真相

CPU 跑 bge-m3 约 **1–2 秒/chunk**。实测证明这不是代码问题：

| 测试 | 结果 |
| --- | --- |
| 服务端日志（单请求） | 85–833ms，抖动来自 CPU 推理本身 |
| 客户端 20 并发 | 801ms |
| 客户端 20 串行 | 863ms |
| 网络往返（复用连接） | 78–111ms |

并发几乎无提升——**Ollama 有全局推理锁**。这是源码里「串行执行」注释的
实证依据，当初的判断是对的。

因此 `embed.batch_size` 只对云端批量接口有意义，对 Ollama 无效
（已在配置示例中注明）。20 份文档 157 chunks 的索引耗时 5 分 26 秒。

要显著提速只能换 GPU 或云端嵌入 API。

## 技术债

| 项 | 说明 |
| --- | --- |
| `LoadVectors` 无容量上限 | 每次检索全量加载向量。10 万片段约 100MB，尚可；更大规模需切到流式扫描 + 堆 |
| 文档级 `embed_model` 标记粗糙 | 一个文档只要部分片段有向量就标记模型名，不区分「部分完成」 |
| 未做向量索引持久化缓存 | 每次检索从 SQLite 读全部 BLOB 再量化比对，无内存缓存层 |
| REPL `/kb list` 不显示向量进度 | 嵌入任务异步跑，列表在任务完成前显示「无向量」 |
