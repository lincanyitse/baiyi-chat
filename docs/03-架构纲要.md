## 1. 总体判断与设计原则

### 1.1 成败取决于三件事

这个项目最终接多少模型并不重要。决定它能走多远的是以下三点：

1. **消息模型是否选对。** 内核必须用 content block 而非扁平字符串。一旦用 `[]string` 作为对话载体，工具结果、图片、思考块、引用全部会被压扁，后期重构等于重写。对应 §3。
2. **上下文组装是否显式、可观测、缓存友好。** 上下文决定回答质量上限；如果无法看清「这一轮到底喂了什么」，调优只能靠猜。对应 §5。
3. **权限与沙箱是否从第一个工具就在协议里。** 工具一旦能写文件、跑 shell，事后补权限会漏调用点。对应 §9、§13。

### 1.2 六条设计原则

| 原则 | 含义 | 反面做法（明确不做） |
| --- | --- | --- |
| 单进程单用户 | 一个二进制、一个数据目录、一个 SQLite 文件 | 不引入服务网格、消息队列、Redis |
| 分层单向依赖 | 只允许上层 import 下层，规则可 lint | 不搞循环依赖、不用 `init()` 隐式注册 |
| 接口只开在真实接缝 | 只有确需替换/多实现的边界才定义接口 | 不给单一实现套接口，不造 `Manager`/`Factory` 包装层 |
| 外部能力 API 化 | 重 AI 能力（嵌入、重排、OCR、ASR）一律出进程 | Go 内不做本地推理、不链接推理库 |
| 数据属于用户 | 全部本地存储、可完整导出、可换模型 | 不做云同步、不做账号绑定 |
| 渐进披露 | 常驻上下文只放「永远需要」的，其余按需加载 | 不把全量技能、全量记忆塞进系统提示 |

### 1.3 全局术语表

| 术语 | 定义 |
| --- | --- |
| Turn（轮次） | 一次用户输入到最终答复的完整过程，可能包含多次模型调用与工具执行 |
| Step（步） | Turn 内的一次模型调用 |
| Block（内容块） | 消息的最小组成单元：文本、图片、工具调用、工具结果、思考等 |
| Provider | 一类模型服务协议的适配器（OpenAI 兼容 / Anthropic 原生 / 国内原生 / 本地） |
| Capability（能力清单） | 某 Provider 某模型支持特性的声明，驱动降级 |
| Tool | 带 JSON Schema 的函数，模型在轮内调用，返回数据 |
| Skill | 目录形态的流程与知识包，按需加载进上下文 |
| ContextSnapshot（上下文快照） | 某一步实际发送给模型的分段内容、token 与裁剪记录 |
| Trace | 一轮内所有模型调用、工具调用、错误的完整记录 |
| Episode（情节记忆） | 一段历史对话的结构化摘要与事件 |
| Fact（语义记忆） | 关于用户的结构化事实（主体 / 谓词 / 值） |
| Jail（路径牢笼） | 把工具可访问的文件系统限制在白名单目录内 |

## 2. 分层与包结构

### 2.1 六层结构

| 层 | 包 | 职责 | 明确不做 |
| --- | --- | --- | --- |
| L5 交付 | `cmd/baiyi` | 进程入口、参数解析、装配根 | 只做 wiring，不含逻辑 |
| L4 应用与接入 | `internal/app` `internal/session` `internal/channel` | 会话管理、轮次编排、持久化调度；渠道协议转换 | `channel` 不含业务逻辑 |
| L3 运行时 | `internal/agent` | Agent Loop、状态机、步数/超时/预算、取消传播、审批挂起、钩子 | 不直连数据库，不 import 具体 Provider |
| L2 能力 | `internal/contextx` `internal/memory` `internal/rag` `internal/skill` `internal/tool` `internal/mcp` | 上下文组装、记忆读写、RAG 管线、技能加载、工具执行、MCP 客户端 | 不感知「第几步」「是否在循环中」，只接受显式入参 |
| L1 协议 | `internal/llm` | 统一消息模型、流式事件、能力清单、用量、错误归一化、Provider 接口 | 纯数据 + 接口 + 错误类型，零副作用，不 import 任何上层包 |
| L0 基础设施 | `internal/infra` | 配置、日志、ID、时钟、HTTP 客户端（重试/代理/脱敏）、密钥、SQLite 连接与迁移 | 不含业务语义 |

### 2.3 依赖规则（可执行）

```
cmd
 └→ bootstrap ─→ channel / session / agent / provider / store
                     │
                     └→ agent ─→ contextx / memory / rag / skill / tool / mcp
                                     │
                                     └→ llm ─→ infra
```

硬规则：

1. **禁止反向 import。** 下层不得 import 上层。强制手段是 `scripts/check-layering.sh`：传递依赖用 `go list -deps`，直接 import 用 `go list -f '{{join .Imports "\n"}}'`。已知债用警告露出，不让检查失败。这里不使用 depguard。
2. **`llm` 包零副作用。** 只允许 import 标准库。任何包都可以安全依赖它。
3. **`agent` 只依赖 `llm.Provider` 接口**，不 import `provider/*` 任何具体实现。具体实现在 `bootstrap/wire.go` 注入。
4. **`tool` 不 import `agent`。** 工具需要的运行时信息通过显式 `ExecContext` 传入（见 §9.1），避免循环依赖。
5. **`channel` 只做协议转换。** Web 依赖自己声明的 `web.Core`（会话、轮次、模型、上下文四组方法），不依赖具体的 `*session.Service`。REPL 是进程内调试入口，仍然持有具体服务。
6. **仓储接口由消费方定义，由 `store/sqlite` 实现。** 这是唯一允许「实现包 import 领域包」的例外：`store/sqlite` → `memory`/`rag`/`session`（仅类型与接口），领域包永不 import `store`。`session` 与 `cost` 不直接 import `infra/sqlite`：会话走 `Repository`，账本只依赖自己的 `DB` 接口。这条由 `check-layering.sh` 的直接依赖检查强制。

### 2.4 接口清单（只开这 6 组）

| 接口 | 定义位置 | 为什么必须是接口 |
| --- | --- | --- |
| `llm.Provider` | `llm` | 四类协议、热切换、测试桩 |
| `tool.Tool` | `tool` | 内置 / MCP / HTTP 工具统一 |
| `tool.Approver` | `tool` | Web 弹窗 / REPL y-n / Bot 按钮各自实现 |
| `rag.Embedder` `rag.Reranker` | `rag` | 外部 API 可替换、可缺失降级 |
| `channel.Channel` | `channel` | 多形态接入 |
| `*Repo`（`memory`/`rag`/`session`） | 各自消费包 | 测试替身、未来换存储 |

**不做抽象的对象**：`Memory`（只有一种实现）、`Skill`（它就是文件）、`Agent`（只有一个 Loop）、`Store`（只有 SQLite）。不要出现 `Engine` / `Manager` / `Factory` 三层同名包装。

## 3. 统一消息模型与流式事件契约

### 3.1 消息与 Block

内核消息模型是全系统的契约根。**所有 Provider 都向它靠拢，而不是相反。**

```go
type Role string

const (
    RoleSystem    Role = "system"
    RoleUser      Role = "user"
    RoleAssistant Role = "assistant"
)

type Message struct {
    ID        string          // UUIDv7
    Role      Role
    Content   []Block         // 有序内容块
    CreatedAt time.Time
    Meta      MessageMeta
}

type MessageMeta struct {
    ParentID    string   // 分支父节点，重生成时使用
    Pinned      bool     // 禁止被摘要压缩
    TrustLevel  Trust    // trusted | user | external
    SourceRefs  []string // 来源：消息 ID / 文档 ID / URL
    Compacted   bool     // 是否已被摘要替代
    TokenCount  int      // 估算值（缓存）
}

type Block interface{ BlockType() BlockType }

type TextBlock      struct{ Text string }
type ImageBlock     struct{ Source ImageSource; Detail string }
type FileBlock      struct{ Name, MediaType string; Data []byte; URI string }
type ToolUseBlock   struct{ ID, Name string; Input json.RawMessage }
type ToolResultBlock struct {
    ToolUseID string
    Content   []Block // 可能含文本或图片
    IsError   bool
    Truncated bool    // 完整结果已落 output_store
    Handle    string  // 取回句柄
}
type ThinkingBlock  struct{ Text, Signature string }
type CitationBlock  struct{ DocID, ChunkID string; Start, End int; Title, URI string }
type AudioBlock     struct{ MediaType string; Data []byte; DurationMS int }
```

**为什么用 Block 而不是扁平字符串**：Anthropic 原生就是块结构；OpenAI 是「字符串 + 旁挂数组」。块模型是超集，反向还原是有损的——工具结果的边界、思考块、引用编号一旦丢失就找不回来。

### 3.2 跨 Provider 规范化规则

这些规则由适配层保证，是所有厂商 400 错误的高发区：

| 规则 | 说明 |
| --- | --- |
| 禁止空文本块 | 空字符串块一律丢弃，否则 Anthropic 直接 400 |
| `tool_result` 必须配对 | 每个 `ToolUseBlock.ID` 必须有且仅有一个结果；反之亦然 |
| 角色交替 | Anthropic 要求 user/assistant 严格交替，相邻同角色消息需合并 |
| system 提升 | Anthropic 的 system 是顶层参数，需从消息数组里抽取合并 |
| 图片位置 | 图片通常只能出现在 user 消息中（由能力清单声明） |
| 思考块回传 | Anthropic 的 `signature` 必须原样带回；DeepSeek 系 `reasoning_content` 反而**不能**回传。是否回传由适配器按 Provider 决定 |
| 工具名约束 | OpenAI 系 `^[a-zA-Z0-9_-]{1,64}$`，超长或含非法字符需确定性改名 + 反查表 |

### 3.3 归一化流式事件

```go
type Event interface{ EventType() EventType }

type StartEvent        struct{ Provider, Model, RequestID string }
type BlockStartEvent   struct{ Index int; Type BlockType }
type TextDeltaEvent    struct{ Index int; Text string }
type ThinkingDeltaEvent struct{ Index int; Text string }
type ToolArgsDeltaEvent struct{ Index int; PartialJSON string }
type BlockStopEvent    struct{ Index int }
type ToolCallReadyEvent struct{ Index int; ID, Name string; Input json.RawMessage }
type UsageEvent        struct{ Input, Output, CachedInput, Reasoning int }
type StopEvent         struct{ Reason StopReason } // end|tool_use|length|filtered|error
type PingEvent         struct{}
type ErrorEvent        struct{ Err *llmError }
```

契约（适配器必须满足，运行时可以依赖）：

1. `BlockStart` 必先于该 index 的任何 delta。
2. `Index` 单调递增，`BlockStart` 的 index 不可复用。
3. `Stop` 或 `Error` **恰好一次**，且是流的最后一条事件。
4. `Stop` 之后不得再有任何 delta。
5. `ToolCallReady` **只在参数 JSON 完整校验通过后**发出（见 §4.4）。
6. `Usage` 可能在最后一个空 choices 分片到达（OpenAI 需显式开启 `include_usage`，极易漏），运行时需容忍它在 `Stop` 之前任意位置出现。
7. OpenAI 没有 block 概念，适配层必须合成为 `BlockStart/TextDelta/BlockStop` 序列。

## 4. Agent 运行时

### 4.1 状态机

```
                       ┌──────────────┐
       新输入 ────────→│    Ingest    │
                       └──────┬───────┘
                              ↓
                       ┌──────────────┐
                       │   Assemble   │  ← 上下文组装，产出快照
                       └──────┬───────┘
                              ↓
                       ┌──────────────┐
                       │    Infer     │  ← 调 Provider，流式
                       └──────┬───────┘
                              ↓
                       ┌──────────────┐
                       │   Decide     │
                       └──┬────┬───┬──┘
              stop_reason  │    │   │ tool_use
                    end ───┘    │   └──────→ ┌──────────────┐
                                │            │   Execute    │
                                │            └──────┬───────┘
                                │                   ↓
                                │            ┌──────────────┐
                                │            │   Refill     │──→ 回到 Infer
                                │            └──────────────┘
                                ↓
                       ┌──────────────┐
                       │  Finalize    │
                       └──────┬───────┘
                              ↓
                       ┌──────────────┐
                       │   Persist    │
                       └──────────────┘

旁支状态：AwaitApproval（审批挂起） / AwaitUser（ask_user） / Canceled / Failed
```

### 4.2 一轮对话的完整时序

1. **Ingest 输入归一化**
   - 渠道差异收敛：Bot 的 @提及、引用消息、平台消息 ID；Web 的附件与 slash 命令。
   - 文本规整：换行统一、零宽字符剔除、超长粘贴折叠、语言检测。
   - 附件转 Block：图片 → `ImageBlock`；文档 → 走 RAG 入库并附 `CitationBlock`。
   - 生成 `turn_id` 与 `client_msg_id`（幂等键），以 `received` 状态写入 transcript。
2. **Assemble 上下文组装**：调用 `contextx.Assembler`，产出 `ContextSnapshot`，见 §5。
3. **Infer 模型推理**：按路由表选 Provider/Model，发起流式请求；事件归一化后转发给渠道，同时写 trace。
4. **Decide 判定**：依据 `StopReason` 决定下一步。
   - `end` → Finalize。
   - `tool_use` → Execute。
   - `length` → 未完成的 tool_call 一律丢弃；转为「续写一次」或收敛并提示截断。
   - `filtered` → 终止并告知用户。
5. **Execute 工具执行**：见 §4.3、§4.4。
6. **Refill 结果回填**：`tool_result` 按 `tool_use` **原始顺序**追加，进入下一轮 Infer。
7. **Finalize**：补发 `Usage` 与 `Stop` 事件，落库最终助手消息。
8. **Persist**：更新 turn 状态，异步触发记忆抽取。

### 4.3 并行工具调用

- 同一条 assistant 消息中的多个 `tool_use` 视为**互相独立**（模型是同时决定的），用 `errgroup` + 信号量并发执行。
- 并发度默认 4，单工具可声明覆盖（如 `web_search` 限 2）。
- 所有工具共享本轮 ctx；任一路径取消则全部取消，被取消的结果标记 `canceled` 并回填给模型。
- **执行并行，回填串行**：结果严格按 `tool_use` 出现顺序追加。Anthropic 要求 `tool_result` 紧跟对应 `tool_use`；OpenAI 要求每条 `tool_call` 对应一条 `role=tool` 消息。
- Provider 能力清单声明不支持并行时（部分本地模型），退化为串行；模型只发一个调用时无需特判。
- **幂等缓存**：`tool_result` 以 `(turn_id, tool_call_id)` 落库。同一 call id 重放直接命中缓存，不重复执行——这既是重试安全的基础，也是「中断后续跑」的基础。

### 4.4 流式工具调用的增量解析

这是最容易吞噬工期的部分，因为各家格式差异极大。

**OpenAI 兼容族**

- `choices[].delta.tool_calls[].index` 标识调用序号。
- `function.arguments` 是**字符串分片**，必须按 `index` 累加拼接。
- `id` / `function.name` 通常只在首片出现，但 vLLM 与部分国内兼容层会每片重发，适配层必须同时容忍「重复且相同」与「首片缺失」。
- 还存在老式 `function_call` 单调用格式，以及个别厂商一次性给完整 JSON（无分片）。

**Anthropic 原生**

- `content_block_start`（`type=tool_use`，带 `id` 与 `name`）→ 多个 `input_json_delta`（`partial_json` 分片）→ `content_block_stop`，按 `content_block index` 缓冲。

**统一处理策略**

1. 解析**只发生在 Provider 适配层**。运行时只接收 `ToolCallStart` / `ToolArgsDelta` / `ToolCallReady` 三种语义事件。
2. `ToolCallReady` 只在 JSON 完整校验通过后发出。
3. 残缺 JSON 依次尝试：宽松修复（补齐括号、去掉尾逗号）→ 仍失败则**不执行**，把错误作为 `tool_result(is_error=true)` 回填，让模型自己重发。
4. **永不 panic、永不阻塞整轮。**
5. UI 层只能展示「正在准备调用 xxx」，不得把半截参数当作最终值呈现。
6. 解析器必须配 fuzz 测试与真实 SSE 录制回放测试（见 §15）。

### 4.5 循环控制默认值

| 参数 | 默认 | 硬上限 | 超限行为 |
| --- | --- | --- | --- |
| 每轮最大步数（模型调用次数） | 12 | 24 | 禁用工具，强制生成最终答复 |
| 单轮墙钟超时 | 180s | 600s | 终止，保留已输出内容 |
| 单次模型调用 | 120s | — | 按错误分类处理 |
| 首 token 超时（TTFT） | 30s | — | 断开重试一次，再失败降级到下一模型 |
| 单次工具执行 | 60s（工具可覆写） | — | 返回超时错误给模型 |
| 每轮工具调用总数 | 20 | — | 强制收敛 |
| 相同工具 + 相同参数重复 | 2 次 | — | 注入提示「你已重复调用，请更换策略」 |
| 每轮成本预算 | 可配 | — | 触发上下文收缩或终止 |

**取消传播**：每轮一个 ctx，派生自会话 ctx。渠道「停止」按钮 → cancel → 取消进行中的 HTTP 请求与工具执行 → 已产出内容以 `assistant(interrupted)` 落库 → 发出 `TurnFinished{reason=canceled}`。所有 goroutine 必须绑定 ctx，禁止裸 `context.Background()`。

### 4.6 错误分类与重试矩阵

统一错误类型：

```go
type Error struct {
    Kind       ErrorKind // 见下表
    HTTPStatus int
    VendorCode string
    Message    string
    RetryAfter time.Duration
    Raw        []byte // 仅进 trace，不进日志正文
}
```

| Kind | 典型场景 | 策略 |
| --- | --- | --- |
| `transient` | 网络重置、5xx、连接超时 | 指数退避 + 抖动，最多 3 次，尊重 `Retry-After`，封顶 30s |
| `rate_limited` | 429 | 同上，退避更保守；同时降低该 Provider 并发 |
| `auth` | 401/403、密钥缺失 | 不重试；标记 Provider 不健康；提示去设置页 |
| `quota` | 余额不足（如 DeepSeek 402） | 不重试；触发路由降级 |
| `invalid_request` | 400、schema 不符 | 不重试；作为开发期 bug 记录并上报 UI |
| `context_overflow` | 超长 | **不算失败**：收缩上下文重试一次，不计入重试次数 |
| `policy` | 内容审核拒绝 | 不重试；原样告知用户 |
| `not_supported` | 能力缺失（如要求视觉但模型不支持） | 触发能力降级后重建请求 |
| `canceled` | 用户取消 | 直接终止 |
| `unknown` | 其他 | 不重试，附原始报文 |

关键规则：

- **已经开始流式输出后不再自动重试**——会重复内容。此时保留已输出部分，向用户暴露「继续」操作（把半截助手消息作为历史，追加用户「继续」，开新一轮）。
- 工具失败**不进**这套分类。工具错误一律转成 `tool_result(is_error=true)` 交给模型自愈；只有「需要人介入」（审批、缺密钥）才挂起整轮。

### 4.7 中断、插话、审批与续跑

| 场景 | 行为 |
| --- | --- |
| 用户硬中断（默认） | 立即 cancel 当前轮，已输出落库为 `interrupted`，新输入立刻开新一轮，并把「用户打断并说了 X」作为事实注入上下文 |
| 用户软排队（可配） | 当前步跑完、在下一次 Infer 前插入用户消息，模型自然看到 |
| 审批挂起 | 整批工具调用一起挂起（模型同批决定，视为互相独立），一次列出全部待确认调用；选项为 `approve` / `deny` / `approve-for-session` / `approve-forever` |
| 审批持久化 | 挂起状态写入 `approvals` 表，进程重启后仍在；超时（默认 10 分钟）自动 deny，并把拒绝原因回填给模型 |
| 续跑 | transcript 是 append-only 步骤日志；重放时跳过已有 `tool_call_id` 的结果，从最后一个未完成步骤继续 |
| 子代理 | `task` 工具启动嵌套 Loop，全新上下文、独立预算、只回传摘要；深度上限 2 层 |

## 5. 上下文工程

### 5.1 八段分层（按稳定性从高到低）

顺序即缓存策略。前 3 段构成**稳定前缀**，第 6–8 段是**追加区**。

| # | 段 | 变化频率 | 内容 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 身份与规则 | 几乎不变 | 人格、约束、输出风格、安全规则 | **禁止**写入时间戳、随机 ID、会话名 |
| 2 | 工具与技能目录 | 工具集变化时 | 工具 JSON Schema + 技能「名字 + 一句话」 | 顺序必须确定，不可每次随机 |
| 3 | 用户画像卡 | 慢变 | 语义记忆的高置信摘要 | ≤300 token |
| 4 | 情节记忆召回 | 每轮可能变 | 相关历史事件摘要 | 条件触发 |
| 5 | RAG 片段 | 每轮变 | 带编号引用的文档片段 | 弹性池 |
| 6 | 对话历史 | 只追加 | 消息数组 | 尽量 append-only |
| 7 | 当前输入与附件 | 每轮 | 用户本轮输入 | **永不裁剪** |
| 8 | 易变便签 | 每轮 | 当前时间、待办、上一步工具摘要 | 放最后，避免污染前缀 |

**硬性要求**：任何对第 1–3 段的逐轮改写都会让前缀缓存全部失效。动态信息一律用工具（`time_now`）或第 8 段承载。

### 5.2 Token 预算

`可用预算 = 模型上下文窗口 − max_output − 安全余量(10%)`

默认分配（可由预设覆盖）：

| 段 | 占比 | 备注 |
| --- | --- | --- |
| 系统与人格 | 8% | 超了精简文本，不要动态化 |
| 工具/技能 Schema | 15% | **硬上限**；超了先减工具数量，再用渐进披露 |
| 用户画像卡 | 5% | |
| 记忆召回 | 5% | |
| RAG | 20% | 最大弹性池 |
| 历史 | 35% | |
| 当前输入 | 5% | 下限保护 |
| 余量 | 7% | |

### 5.3 超限降级顺序（严格按序，不可跳步）

1. 丢弃 RAG 中重排分数最低的片段，并去重。
2. 压缩用户画像卡（只保留高频、高置信条目）。
3. **历史工具结果换桩**：超过 N 轮的大块 `tool_result` 替换为「结果已保存，句柄 xxx，可用 `tool_output_read` 取回」。这是性价比最高的机制，第一版就要有。
4. 触发滚动摘要压缩最老的历史块（见 §5.4）。
5. 丢弃超过下限的最老轮次。
6. 仍然超限 → **明确报错**，不静默截断。

禁止事项：静默从中间截断对话；截断当前用户输入；把工具 schema 截半。

### 5.4 滚动摘要

- 状态表 `summary_state{ session_id, covered_through_seq, summary, extracted_facts, template_version }`。
- **触发**：历史 token 超过其配额 60%，或距上次压缩超过 15 轮，或会话空闲 5 分钟。
- **策略**：一次性压缩最老的约 50%，压到约 25%；保留最近 8–12 轮（约 4–8k token）原文作为「近期尾巴」。**不做每轮滑窗式细碎压缩**——每次压缩都会让压缩点之后的前缀缓存全部失效。
- **摘要用固定结构**，不用自由发挥：
  1. 决策与结论
  2. 未决问题
  3. 实体与人名
  4. 用户偏好与新事实
  5. 工具产出与句柄
  6. 用户显式要求
- 结构化摘要可校验、可抽取进记忆、可比对。
- 用户可「钉住」某条消息，永不压缩。
- **分支**：用户编辑或重新生成消息会让该点之后的历史失效。必须显式记录分支（`parent_message_id`），不得原地改写历史。

### 5.5 跨 Provider token 计数

三档机制，缺一不可：

| 档 | 机制 | 说明 |
| --- | --- | --- |
| 事后真值 | 以 Provider 返回的 usage 为准 | 含 cached tokens；是最可信的数据 |
| 事前估算 | `Estimator` 接口，按 model 选策略 | OpenAI 系用 tiktoken Go 实现（编码表随二进制打包，禁止运行时下载）；Anthropic 用 `count_tokens` 接口（有网络成本，做 LRU，只对接近上限的请求调用）；其他/本地用启发式（中文 0.6–0.8 token/字，英文 1 token/3.5 字符，保留 10–15% 余量） |
| 自动校准 | 按 `(provider, model)` 存 `(估算, 实际)`，EWMA 算修正系数 | 模块很小，但能让预算长期准确 |

图片按各 Provider 规则折算为固定 token（Anthropic 按像素面积，OpenAI 按 `detail` 分档）。

### 5.6 上下文快照

每次 Infer 落一条 `context_snapshots` 记录：

- 各段内容（或内容寻址引用，避免重复存储）
- 各段 token 估算与实际 usage
- 被裁剪 / 被压缩的条目及原因
- 缓存断点位置
- 每段内容哈希
- 与上一轮的 diff（标出「哪一段变了导致缓存失效」）

这是调优 Agent 质量唯一靠谱的工具，比任何日志都好用。M1 必须交付，不能拖到后期。

### 5.7 M1 实施要点（已落地）

落地时补充的几条约束，值得记录：

- **降级停止条件不能只看总量**。单个弹性段（如 RAG）可能自身超出配额而总量仍有余量——配额分配的意义就是限制单段膨胀，所以每一级降级都要独立判断。
- **段级裁剪顺序写死为切片**，不注册、不插拔。架构要求「严格按序不可跳步」，可配置化只会制造漂移。
- **本轮工具往返必须完整保留**（`LiveTurns`），否则 `tool_use`/`tool_result` 配对会断，模型直接 400。它们同时要计入快照，否则诊断信息失真。
- **摘要必须是六段固定结构**，缺段判失败并保留旧摘要。自由发挥的摘要在长会话里会逐渐丢失关键信息。
- **摘要走 `route.summarize`**，内部任务应使用便宜模型。

## 6. 记忆子系统

### 6.1 四类记忆

| 类型 | 内容 | 存储 | 召回方式 |
| --- | --- | --- | --- |
| 工作记忆 | 当前会话 transcript、临时便签 | `messages` + 内存缓冲 | 直接在上下文里 |
| 情节记忆 | 会话摘要、事件、时间线 | `episodes` | 语义相似 + 时间衰减 |
| 语义记忆 | 用户事实、偏好、画像条目 | `facts` | 画像卡常驻 + 检索 |
| 程序记忆 | 技能、习惯性流程 | `skills/` 目录 + `skill_index` 表 | 技能目录 + 按需加载 |

边界判定：「用户喜欢简短回答」是语义记忆的偏好类；「怎么做某件事」是程序记忆。

### 6.2 写入时机

| 触发 | 方式 | 说明 |
| --- | --- | --- |
| 显式记忆 | 用户说「记住…」或点击「记下」 | 立即写入，回显「已记住：…」，可撤销 |
| 轮次后抽取 | 异步，小模型 | 默认每 10 轮一次，不阻塞回复；只抽高精度候选 |
| 会话结束总结 | 异步 | 生成情节摘要 + 事实候选 + 未决事项 |
| 外部内容 | **不自动写入** | 网页 / RAG 中的事实标记 `source=external`、低信任，不进入画像卡 |

### 6.3 候选 → 合并管线

**所有写入都走这条管线，绝不直接 insert。**

```
抽取 → 候选
   ↓
去重（精确匹配 + 向量近邻）
   ↓
检索相似事实 top-3
   ↓
判定：duplicate / update / contradict / unrelated
   ↓
合并（更新置信度、写版本、记录来源）
```

这是防止记忆污染的唯一有效手段。

### 6.4 召回双通道

- **每轮预召回（常驻）**：画像卡（≤300 token）+ 条件触发的情节召回（用户出现「上次」「之前」「那个项目」等时间/指代线索时取 top-3）。SQLite 查询 <10ms，延迟可忽略。
- **主动检索（工具）**：`memory_search`，支持时间范围、实体、类型过滤。

判断标准：预召回只放「永远都该知道」的；「可能需要知道」的交给工具。全量注入既烧预算又稀释指令遵循。

### 6.5 冲突、版本与衰减

- `facts` 按 `(subject, predicate)` 维护当前真值，同时保留完整版本历史（`valid_from` / `valid_to` / `superseded_by`），**只追加不删除**。
- 优先级：**用户显式陈述 > 用户隐含推断 > 外部内容**；新且高置信 > 旧；被反复确认 > 单次出现。
- 高置信事实被新事实冲突时，不静默覆盖：标记 `disputed`，在下次相关对话中向用户确认（「之前你说 X，现在改成 Y 了吗？」）。
- 注入优先级 = `重要性 × 时间衰减 × 访问频次`。情节记忆半衰期约 90 天；语义事实内容不衰减，只降注入优先级。
- 低于阈值 → **归档**（仍可被工具检索，不再注入），不物理删除。物理删除仅由用户主动执行。
- 用户显式写入的记忆永不自动遗忘。

### 6.6 向量存储

- 向量以 BLOB 存 int8（写入时量化），原始 f32 只用于写入与 top-50 精排。
- 向量表**必须记录 `embedding_model` 与 `dim`**。换嵌入模型是必然事件，从第一天就要能识别旧模型向量并触发重嵌。
- **chunk 与 episode 共用一张 `embeddings` 表**，用 `owner_kind('chunk'|'episode') + owner_id + model` 作主键：重建、量化、扫描、幂等键只写一次。
- 三档规模策略：

| 规模 | 策略 | 内存 |
| --- | --- | --- |
| < 15 万行 | 进程内 int8 矩阵，按需加载，空闲 10 分钟释放 | 约 100MB |
| 15 万+ | SQLite 流式扫描 + 容量 K 的堆 | O(K) |
| 更大 | 接外部向量库 | — |

估算依据：20 万 × 1024 维 × 4B = 819MB，**全载入 f32 不可接受**；量化到 int8 后降到可接受范围。

### 6.7 M2.2 实施要点（已落地）

- **嵌入接口放 `internal/embed`，不放 `rag`**（ADR-0015）。记忆的情节向量化也要用嵌入，放 rag 会强制 `memory → rag`。
- **规则优先，不上小模型**：去重与冲突判定走归一化键 + 字面相似度，热路径零额外调用。
- **画像卡不做每轮 LLM 重写**：措辞每轮变会让稳定前缀抖动。改为按事实渲染，只在 facts 变更时重算。
- **预召回纯 SQL**：查询嵌入是网络调用（30–100ms），不能放热路径。
- **外部内容三层强制隔离**：工具侧按污点降级来源、写入器按优先级拒绝覆盖、查询 SQL 硬过滤。

实施中修正了计划里的三处判断，详细记录见 [10-M2.2完成报告](./10-M2.2完成报告.md)：

| 计划 | 实际 | 原因 |
| --- | --- | --- |
| 情节向量化走 `internal/embed` | 未使用嵌入 | 情节只有几百条，纯 SQL 召回足够；不依赖嵌入意味着最小配置也能用记忆 |
| 相似度用 bigram Jaccard ≥ 0.9 | 加前缀规则（差额 ≤2 字） | 「北京」vs「北京市」的 Jaccard 只有 0.5，判不出相同 |
| 未规定 `memory_write` 风险等级 | `RiskRead` | 初设 `RiskWrite` 导致每写一条记忆都要按 y；记忆只影响本地库且随时可撤销 |

另外两条计划外但必须遵守的约束：

- **唯一索引要求「先让位再插入」**：`(subject_key, predicate_key)` 只允许一条 `active`，update 路径必须在一个事务里先标记旧行 `superseded`。
- **中文线索词要切二元组**：情节召回按线索词匹配，中文没有词边界，按空格切会整句变成一个词项。

## 7. RAG 管线

### 7.1 阶段分工

| 阶段 | Go 侧自建 | 外部 API | 关键坑 |
| --- | --- | --- | --- |
| 接入 | 上传（Web multipart）、URL 抓取、本地目录（白名单 + 可选 watcher）、内容哈希去重 | — | 本地目录要防误扫（`node_modules`、`.git`） |
| 解析 | Markdown（goldmark）、HTML（readability + x/net/html）、纯文本 | 扫描版 PDF / 图片 OCR、复杂 docx/xlsx | 保留原文 blob（内容寻址存盘），文本进库 |
| 切分 | 结构化优先：标题 → 章节 → 段落 → 定长兜底；400–800 token，10–15% 重叠；携带标题路径面包屑 | — | 表格与代码块不切；中文按句子边界 |
| 嵌入 | 批处理（32–128/批）、限流、重试、成本记账 | **Embedding API** | 记录模型与维度；超长文本先截断 |
| 索引 | SQLite：`documents` / `chunks` / `chunks_fts` / `embeddings` / `jobs` | — | **FTS5 默认分词器对中文几乎不可用**，见 §7.2 |
| 检索 | 向量 top-30 + 关键词 top-30 → RRF(k=60) 融合 | 可选外部向量库 | 向量服务挂掉时须能退化为纯关键词 |
| 重排 | 编排与降级 | **Rerank API** | 不可用时退化为 RRF 分数，不报错 |
| 引用 | chunk → 文档 + 偏移，生成 `[n]` 编号与深链 | — | 引用必须能点回原文位置 |
| 增量 | `content_hash` + 更新时间，只重嵌变更 chunk；删除文档级联清向量 | — | |

Go 侧负责整条编排；外部 API 只负责重活：嵌入、重排、OCR、复杂文档解析。

### 7.2 中文全文检索（M0 必须冒烟验证）

FTS5 内置分词器（`unicode61`、`porter`）对中文按字符切分，检索质量极差。可选方案：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A. 应用层 bigram（推荐）** | 写入影子列时把中文切成二元组（「白泽助手」→「白泽 泽助 助手」），查询同样切分 | 纯 Go、无依赖、效果可用；索引体积约 2 倍 |
| B. 自定义分词扩展 | 编译 SQLite 分词器 | 与 `CGO_ENABLED=0` 冲突，放弃 |
| C. 退化为 LIKE + 向量 | 关键词路用 `LIKE`，主要靠向量 | 简单但慢且召回差 |

结论：M0 做方案 A 的冒烟测试；若不达标，退化到 C 并把结论记录进 ADR。

### 7.3 检索策略

- 查询侧默认单次检索。
- 指代不明的查询做一次改写（1 次小模型调用，可开关）。HyDE 暂不做。
- 个人规模用「全库检索」即可，多集合路由等语料变大再说。

### 7.4 M2.1 实施要点（已落地）

- **不在热路径预取**：查询嵌入是网络调用，会击穿 NFR-PERF-001（本地开销 <100ms）。RAG 由模型调 `rag_search` 工具，结果以 `tool_result` 回填——同 `load_skill` 的先例。
- **切分在解析期就产出带类型的块**：`Kind ∈ {heading, para, table, code}`，表格与代码是原子块不切。
- **bigram 分词保留 ASCII 整词**：否则 `RAG` 会变成 `RA AG` 造成误命中。
- **FTS5 建表语句必须单行**：迁移执行器按行尾分号切分。
- **重排不可用不报错**：退化为 RRF 分数并在结果首行注明。

实施中修正了计划里的两处判断，详细记录见 [09-M2.1完成报告](./09-M2.1完成报告.md)：

| 计划 | 实际 | 原因 |
| --- | --- | --- |
| FTS5 用 `content=''` + `contentless_delete=1` 省体积 | 用普通 FTS5 表 | contentless 表的 `chunk_id` 是 UNINDEXED 列，`DELETE ... WHERE chunk_id = ?` 匹配不到行，删除文档会留孤儿 |
| 查询包成单个 phrase | 拆成多个 phrase 并分严格/宽松两档 | 二元组跨词边界会切出原文不存在的组合（「白泽助理」→「泽助」），整串 phrase 必然零命中 |

另外两条计划外但必须遵守的约束：

- **切分必须跨 Section 打包**：解析器把每个段落产成一个 Section，逐个切分会让打包与重叠完全失效。
- **字符偏移由解析器给出**：切分器推算要跨过标题与空行，必然偏小，引用会跳到错误段落。

向量共用一张表的设计（§6.6）已落地并验证：主键含 `model`，新旧模型向量并存，
切回旧模型时零次嵌入调用即恢复。CPU 跑 bge-m3 实测 1–2 秒/chunk，
并发无收益（Ollama 有全局推理锁），换 GPU 或云端 API 才能显著提速。

## 8. 技能规范

### 8.1 Tool 与 Skill 的边界

| | Tool | Skill |
| --- | --- | --- |
| 本质 | 带 schema 的函数，返回数据 | 打包的流程 + 知识 + 素材 |
| 作用 | 扩展「能做什么」 | 改变「怎么想、按什么步骤做」 |
| 形态 | 编译期代码 或 MCP | 目录 + Markdown 文件 |
| 调用者 | 模型在轮内调用 | 模型按需加载进上下文 |
| 判据 | 需要执行 IO / 计算并拿回结果 | 需要进入上下文影响行为 |

### 8.2 目录格式

```
skills/<name>/
├── SKILL.md          # 必需：YAML frontmatter + 正文
├── references/*.md   # 可选：按需读取的参考资料
├── scripts/*         # 可选：脚本（执行需审批）
└── assets/*          # 可选：素材
```

`SKILL.md` frontmatter：

```yaml
---
name: meeting-notes
description: 把会议记录整理成结构化纪要与待办
version: 1.0.0
spec: 1                 # 规范版本
triggers:               # 确定性触发（可选）
  - "会议纪要"
  - "整理会议"
allowed-tools:          # 激活后建议可用的工具
  - memory_search
  - rag_search
requires:               # 依赖声明
  - skill: note-format
---
正文（Markdown）：流程、规则、示例、判据。
```

### 8.3 三级渐进披露

| 级别 | 内容 | 常驻成本 |
| --- | --- | --- |
| L0 目录 | 名字 + 一句话描述 | 每个约 50–80 token |
| L1 正文 | `SKILL.md` 主体（调用 `load_skill` 或命中触发器后加载） | 按需 |
| L2 参考 | `references/*.md`，由模型用文件读取工具按需取 | 按需 |

### 8.4 触发方式

| 方式 | 说明 |
| --- | --- |
| 手动 | UI 的 `/技能名` 或按钮强制激活 |
| 自动（主路径） | 把 L0 目录交给模型，由模型自行判断并调用 `load_skill`。比单独训分类器简单，且随模型能力提升自然变好 |
| 确定性 | frontmatter 的 `triggers` 命中关键词/正则即激活，用于「永远要遵守」的规矩类技能 |
| 预设绑定 | 某个 Agent 预设把技能设为常驻 |

技能是**数据不是代码**，可完全运行期热加载（目录扫描 + 校验）。

## 9. 工具协议与 MCP

### 9.1 统一接口

```go
type RiskLevel int // Read | Write | Dangerous

type Spec struct {
    Name        string          // 面向模型，受 ^[a-zA-Z0-9_-]{1,64}$ 约束
    Description string          // 必须写清「什么时候不要用」
    InputSchema json.RawMessage // 由 Go struct 生成，additionalProperties:false
    Risk        RiskLevel
    Timeout     time.Duration
    Idempotent  bool
    MaxConc     int             // 并行上限，0 用默认
    Examples    []Example
}

type Tool interface {
    Spec() Spec
    Execute(ctx context.Context, in json.RawMessage, ec *ExecContext) (Result, error)
}

type ExecContext struct {
    SessionID string
    TurnID    string
    WorkDir   string          // 路径牢笼根
    Approver  Approver        // 需要确认时调用
    Taint     TaintState      // 是否消费过外部内容
    Outputs   OutputStore     // 大结果落盘
    Logger    *slog.Logger
}

type Result struct {
    Blocks []llm.Block // 通常是 TextBlock，也可含 ImageBlock
    IsError bool
}
```

### 9.2 权限分级

| 等级 | 例子 | 策略 |
| --- | --- | --- |
| `read` | 记忆检索、RAG 检索、网页读取 | 自动执行 |
| `write` | 写文件、发消息 | 牢笼内自动 + 审计；越界或首次操作需确认 |
| `dangerous` | shell、删除、外发邮件、付款 | **永远确认**，不提供「永久允许」 |

策略维度：按工具、按路径白名单、按主机白名单、按会话。

审批交互抽象为 `Approver` 接口，Web 弹窗 / REPL y-n / Bot 按钮 / CLI flag 各自实现；超时自动拒绝。

### 9.3 结果截断与句柄

- 按 token 与字节**双上限**截断（默认 8k token / 32KB）。
- 完整结果落 `tool_output_store`（内容寻址文件），返回句柄。
- 模型可用 `tool_output_read` 按句柄分段取回。

这是上下文预算降级的关键配套（见 §5.3 第 3 步）。

### 9.4 MCP 客户端

| 方面 | 设计 |
| --- | --- |
| 传输 | stdio（本地子进程）、Streamable HTTP（远程首选）、旧版 HTTP+SSE（兼容保留） |
| Windows 注意 | 很多 server 是 node/npx，需要 `cmd /c` 包装 |
| 命名空间 | 内部名 `mcp__<serverAlias>__<tool>`；暴露给模型时映射为确定性短名 + 反查表，满足 64 字符与字符集限制 |
| 冲突 | 两个 server 暴露同名工具时用别名区分，**绝不静默丢弃** |
| 生命周期 | 启动时懒连接；`tools/list` 后做能力快照；监听列表变更通知 |
| 容错 | 单个 server 挂掉只把它的工具标记为不可用并告知模型，不拖垮启动 |
| 内容映射 | MCP 的 text/image/resource 映射进 `Block`；resources/prompts 后期可映射为 RAG 源或技能 |
| 安全 | MCP server 是任意代码：按 server 配置工具白名单，危险工具默认不暴露；其工具描述视为**不可信输入**（注入面） |

### 9.5 首期内置工具最小集

| 工具 | 风险 | 为什么首期就要 | M1 状态 |
| --- | --- | --- | --- |
| `time_now` | read | 让系统提示不必塞动态时间，保护前缀缓存 | ✅ 已实现 |
| `web_fetch` | read | URL → 正文，限制大小与超时 | ⬜ 待做 |
| `web_search` | read | 外部搜索 API，可插拔（Tavily / Bocha / Serper） | ⬜ 待做 |
| `memory_search` | read | 主动记忆检索 | ⬜ M2 |
| `memory_write` | write | 显式记忆 | ⬜ M2 |
| `rag_search` | read | 知识库检索 | ⬜ M2 |
| `load_skill` | read | 技能渐进披露入口 | ✅ 已实现 |
| `tool_output_read` | read | 取回被截断的工具输出 | ✅ 已实现 |
| `ask_user` | read | 结构化澄清，被严重低估 | ✅ 已实现 |

后期再上：文件读写、shell、浏览器自动化、日程、子代理 `task`。

### 9.6 M1 实施要点（已落地）

**MCP 客户端**（`internal/mcp`）：

- SDK 选官方 `modelcontextprotocol/go-sdk` v1.8.0，锁精确版本
- stdio 走 `CommandTransport`（接受 `*exec.Cmd`），不是 `StdioTransport`——后者只用于当前进程的 stdin/stdout
- **Windows 必须 `cmd /c` 包装**：`npx`、`node` 是 `.cmd` 批处理，`exec.Command` 无法直接执行；同时设 `HideWindow` 避免弹黑框
- 工具名 `mcp__<alias>__<tool>`，超 64 字符或含非法字符时退化为 `mcp_<alias>_<fnv32a>` 短名，确定性可反查
- **MCP 工具描述与返回内容一律视为不可信外部输入**：描述加来源标注，返回值标记污点

**审批与污点追踪**：

- 只读工具自动放行；写与危险操作需确认
- **污染后取消已授权豁免**：一旦本轮消费过外部内容，先前的「永久允许」不再可信
- 危险操作不提供「永久允许」选项
- panic 也必须写入幂等缓存，否则续跑会重复执行

**技能**（`internal/skill`）：

- 目录指纹用**内容哈希**而非 mtime——Windows 上同秒改写的 mtime 不可靠
- `load_skill` 的正文以 `tool_result` 形式入上下文，**不写进 system**：否则段 2 每轮变化，整段前缀缓存失效
- 确定性触发（命中 `triggers`）注入 Notes 段（段 8），同样不污染前缀

## 10. Provider 抽象与路由

### 10.1 Provider 接口

```go
type Provider interface {
    Name() string
    Capabilities(model string) Capabilities
    Stream(ctx context.Context, req Request) (EventStream, error)
    CountTokens(ctx context.Context, req Request) (int, error) // 不支持时返回 ErrUnsupported
    Health() Health
}
```

### 10.2 能力清单

```go
type Capabilities struct {
    ContextWindow     int
    MaxOutput         int
    Tools             bool
    ParallelTools     bool
    ToolChoiceModes   []string
    Vision            bool
    Audio             bool
    Thinking          bool
    PrefixCache       bool
    MinCacheTokens    int
    StructuredOutput  bool
    StrictSchema      bool
    RequiresAlternate bool   // 是否要求角色严格交替
    ToolNamePattern   string // 如 ^[a-zA-Z0-9_-]{1,64}$
    MaxToolResultBytes int
    Tokenizer         string
    PriceIn, PriceOut, PriceCached float64
    Currency          string
}
```

**能力是「协商」不是「事实」**：自建 vLLM / Ollama 的差异极大，配置必须能覆盖声明。请求构建时若所需能力未声明，就走降级（丢图、关并行、拆工具），而不是发出去等 400。

### 10.3 四类 Provider 的实现策略

| 类型 | 首期 | 说明 |
| --- | --- | --- |
| OpenAI 兼容（Chat Completions） | **完整实现** | 覆盖 DeepSeek / Qwen / GLM / Kimi / vLLM / Ollama 等绝大多数 |
| OpenAI Responses（`/v1/responses`） | **完整实现** | 事件结构与 Chat 不同（output item、reasoning summary、function_call item），独立适配器 |
| Anthropic 原生 | **完整实现** | 工具调用与缓存机制差异大，必须独立适配器 |
| 国内厂商原生 | 按 OpenAI 兼容接入 | 等出现不可绕过的差异（如特殊签名、私有字段）再做原生适配 |
| 本地模型 | 按 OpenAI 兼容接入 | 额外处理：无密钥、超时放大、并发压低、Ollama 需显式设 `num_ctx` |

结论：真正的「第二实现」是 Anthropic 与 Responses。翻译复杂度全部关在适配层，运行时只认归一化事件。

### 10.4 Anthropic 原生 vs OpenAI 兼容 关键差异

| 维度 | Anthropic 原生 | OpenAI 兼容 |
| --- | --- | --- |
| 系统提示 | 顶层 `system` 参数 | `role:system` 消息 |
| 工具定义 | `input_schema` | `function.parameters` |
| 工具调用位置 | assistant 消息内的 `tool_use` 块 | 消息上的 `tool_calls` 数组 |
| 工具结果 | user 消息内的 `tool_result` 块（可与文本混排） | 每条结果一条 `role:tool` 消息 |
| 结束原因 | `stop_reason: tool_use` | `finish_reason: tool_calls` |
| 流式 | 具名事件 + 按 index 的块生命周期 | `choices[].delta` + `tool_calls[].index` + 参数字符串分片 |
| 角色 | 严格交替 | 松散，含 `tool` / `function` |
| 用量 | `input_tokens` / `output_tokens` / `cache_read` / `cache_creation` | `prompt_tokens` / `completion_tokens` / `prompt_tokens_details.cached_tokens` |
| 缓存 | 显式 `cache_control` 断点（最多 4 个） | 自动前缀缓存（通常 ≥1024 token 起，按块对齐） |
| 思考 | `thinking` 块 + `signature` 必须保留 | 非标准 `reasoning_content`，多数不可回传 |
| 严格 schema | 宽松 | strict 模式要求全字段必填且禁止额外字段 |

**适配层的复杂度和价值几乎全在这张表的后三行。**

### 10.5 错误归一化

OpenAI 兼容生态是「错误码动物园」：DeepSeek 用 402 表示余额不足，各家有自有业务码，Ollama 可能返回纯文本。适配层负责映射到 §4.6 的统一 Kind，**绝不让厂商原始错误码冒到运行时**。

### 10.6 路由

声明式路由表，按**任务类型**键控：

```toml
[route.chat]
candidates = ["deepseek/deepseek-chat", "anthropic/claude-sonnet-5-5", "local/qwen3-32b"]

[route.tool_use]
requires = ["tools"]
candidates = ["anthropic/claude-sonnet-5-5", "deepseek/deepseek-chat"]

[route.extract_memory]
candidates = ["local/qwen3-8b", "deepseek/deepseek-chat"]

[route.vision]
requires = ["vision"]
candidates = ["anthropic/claude-sonnet-5-5", "qwen/qwen-vl-max"]

[route.embed]
candidates = ["embed/bge-m3"]

[route.rerank]
candidates = ["rerank/bge-reranker-v2"]
```

- 每个条目 = 有序候选列表 `(provider, model, 约束)` + 降级链。
- 只有可重试错误才降级（`invalid_request` 降级没意义）。
- 内部任务（摘要、记忆抽取、标题生成）走便宜模型。
- 用户可在会话级手动指定模型；隐私模式可强制走本地。
- **不做学习型路由**。个人项目里，一张配置表 + 手动覆盖 > 任何自动路由。
- Provider 连续失败 N 次进入冷却期，期间跳过。
- 模型别名 `fast` / `smart` / `vision` / `local` → 具体 provider/model；UI 显示别名，日志与账单显示具体型号。

### 10.7 密钥与配置

```toml
[providers.deepseek]

base_url  = "https://api.deepseek.com/v1"
api_key_env = "DEEPSEEK_API_KEY"      # 只引用环境变量，不内联密钥
[providers.deepseek.models."deepseek-chat"]

context_window = 128000
max_output     = 8192
vision         = false

```

少量本机使用可选用 Windows DPAPI 加密的 `secrets.dat`。日志与 HTTP 客户端**双向脱敏**，密钥绝不允许出现在 trace、导出包、错误信息里。

### 11.2 设计约定

- **主键一律 UUIDv7**（时间有序）。虽然现在不做多设备同步，但数据模型必须留这个缝：将来同步时不必重写存储层。
- **软删除 + 墓碑**：所有用户可见实体带 `deleted_at`。
- **所有实体带 `created_at` / `updated_at`**。
- **append-only**：`messages` 只追加，编辑与重生成产生新分支（`parent_id`），历史不变。
- **迁移**：内嵌 SQL 文件（`go:embed`）+ `PRAGMA user_version`，启动时顺序执行；迁移前自动备份数据库文件。
- **WAL 模式**，`busy_timeout=5000`，`foreign_keys=ON`。

## 12. 可观测性与回放

### 12.1 Trace 结构

一轮的完整轨迹：

```
Turn trace
 ├─ step 1
 │   ├─ context_snapshot (segments, tokens, trims)
 │   ├─ llm_call (provider, model, tokens, latency, ttft, cost, error?)
 │   ├─ events（文本增量已折叠，只记首尾与长度）
 │   └─ tool_calls[]
 │        ├─ name, args, risk, approval(rule/action/who)
 │        ├─ result（或 handle）, is_error, duration
 │        └─ truncated?
 ├─ step 2 ...
 └─ finalize (reason, total tokens, total cost)
```

### 12.2 回放

- 支持「用同样上下文对同一模型重跑」与「对另一模型重跑并对比」。
- 回放依赖 `context_snapshots` + `llm_calls`，无需重新组装上下文。
- 对比视图输出：文本差异、token 差异、工具调用差异、耗时差异。

### 12.3 成本记账

- 每次模型调用写一行 `llm_calls`。
- 价格表 `prices` 是**带生效日期的数据**，不是代码常量（价格会变，且需支持多币种）。
- UI 提供日 / 月汇总与「本会话花了多少」。
- 嵌入与重排调用同样记账（`purpose=embed/rerank`）。

### 12.4 日志

**两级职责，不要混用**：

| 类别 | 去向 | 内容 | 落盘 |
| --- | --- | --- | --- |
| 系统日志 | `internal/infra/logx` 产出的 `slog.Logger` | 启动摘要、轮次摘要、模型失败、记账/状态更新失败、降级 | 是（JSON + 轮转） |
| 界面输出 | 渠道自己写 stdout | 对话内容、提示符、进度 | 否 |

日志文件只记系统事件。需要回放对话时查 `messages` 表，不要靠日志——否则日志会被聊天内容淹没，且与数据库重复存储。

- `log/slog` 结构化日志；控制台人类可读，文件为 JSON 行 + 按大小轮转。
- **脱敏 handler 包在最外层**：属性名命中 `api_key` / `authorization` / `token` / `secret` / `password` / `cookie` / `credential` 即替换为 `***`；值内嵌的 `Bearer <token>` 与 URL 查询参数同样处理；递归覆盖 `slog.Group` 与 `With()` 绑定。
- 启动失败分两段：logger 建立**之前**的失败只到 stderr（此时无处可写）；**之后**的失败必须落盘，并向用户提示日志路径。用 `bootstrap.StartupError.LogFile` 区分，避免提示一个空日志。
- trace id 命名与 OpenTelemetry 兼容，但**暂不接入 OTel**。

## 13. 安全设计

### 13.1 路径牢笼（Windows 重点）

```go
func ResolveJail(root, p string) (string, error) {
    abs := filepath.Clean(filepath.Join(root, p))
    real, err := filepath.EvalSymlinks(abs)   // 解析 junction / symlink
    if err != nil { return "", err }
    rootReal, _ := filepath.EvalSymlinks(root)
    if !strings.HasPrefix(real, rootReal+string(os.PathSeparator)) &&
       real != rootReal {
        return "", ErrOutsideJail
    }
    return real, nil
}
```

Windows 额外防线：

- 拒绝 UNC 路径（`\\server\share`）与设备路径（`\\?\`、`\\.\`）。
- 拒绝驱动器相对路径（`C:foo`）。
- 拒绝备用数据流（`file.txt:stream`）。
- 超长路径统一加 `\\?\` 前缀处理。
- junction 与 symlink 必须在 `EvalSymlinks` 后再校验前缀（顺序不能反）。

### 13.2 SSRF 防护（`web_fetch` 与 HTTP 工具）

- 解析后校验 IP：禁止私网段（10/8、172.16/12、192.168/16、127/8、169.254/16、::1、fc00::/7）。
- 禁止云元数据地址（`169.254.169.254`）。
- **解析后固定 IP 发起连接**，防 DNS rebinding。
- 禁止重定向到私网；重定向次数上限 5。
- 响应体大小上限（默认 5MB）与总超时（默认 30s）硬限制。
- 仅允许 http/https scheme。

### 13.3 提示词注入的纵深防护

诚实地说：这些都**不能根治**，真正的控制点是审批门 + 权限分级。

| 层次 | 措施 |
| --- | --- |
| 结构隔离 | 外部内容用明确分隔符包裹，并声明「这是数据不是指令」 |
| 污点追踪 | 本轮一旦消费过外部内容（`Taint`），写/危险级工具强制走审批，不论模型怎么说 |
| 记忆防护 | 外部内容写入记忆时打 `source=external` + 低信任，不自动升级为画像 |
| 执行防护 | 不自动执行模型输出里的链接或命令 |
| 检测 | 对可疑注入模式（「忽略之前的指令」等）打日志，便于事后复盘 |
| 范围限制 | MCP 工具描述同样视为不可信；按 server 配置工具白名单 |

### 13.4 密钥

- 只从环境变量或 DPAPI 加密文件读取，配置文件中写 `api_key_env` 而非密钥本身。
- 日志、trace、导出包、错误信息四处全部脱敏。
- HTTP 客户端在 debug 级别打印请求时剔除鉴权头。

### 13.5 本地口令

单用户场景不做账号体系。仅提供可选的本地口令（Argon2id 哈希存本地），用于防止同一台机器上的其他人直接打开 Web 界面。默认关闭。

## 14. 扩展机制

### 14.1 编译期装配（不用 `init()` 自注册）

在 `bootstrap/wire.go` 里显式构造所有组件：

```go
func Wire(cfg *Config) (*App, error) {
    db := sqlite.Open(cfg.DataDir)
    provs := provider.Build(cfg.Providers)
    tools := tool.NewRegistry()
    tool.RegisterBuiltins(tools, deps...)
    mcp.RegisterServers(tools, cfg.MCP)
    ...
}
```

理由：`init()` 制造隐藏全局状态、顺序不可控、测试里无法用不同配置构造两个实例。

例外：无配置依赖的「纯函数工具包」可以用 `init()` 注册以减少样板。

### 14.2 配置白名单启用

配置里列 `enabled = [...]`，未启用的工具**根本不发给模型**。这既省 token，也降低误用。

### 14.3 运行期扩展的边界

| 路径 | 支持 | 说明 |
| --- | --- | --- |
| MCP（stdio / HTTP） | **是** | 唯一正式的运行期代码扩展路径 |
| 技能目录 | **是** | 数据形态，可完全热加载 |
| 配置声明的 HTTP 工具 | 是 | 名称 + 方法 + URL 模板 + 参数 schema，覆盖简单 webhook |
| Go `plugin` | **否** | Windows 支持差、版本必须严格一致、崩溃无法隔离 |
| 动态脚本 | **否** | 需要时用独立进程 + 协议（MCP 已是该形态） |

### 14.4 版本兼容

所有持久化/结构化产物带版本号：

- `SKILL.md` 的 `spec` 与 `version`
- 工具 schema 版本
- 提示模板版本
- 数据库 schema 版本（`user_version`）

提示模板作为**带版本的数据文件**（`go:embed`），而非散落在代码里的字符串常量：可对比、可回滚、可在 trace 中记录版本号，从而把「回答质量变化」与「模板改动」关联起来。

### 14.5 Agent 预设与子代理

预设 = 一份 YAML：人格提示、启用的技能/工具集、记忆命名空间/过滤、默认模型路由、温度、预算覆盖、输出风格。用户按场景切换（工作 / 学习 / 代码 / 闲聊）。预设共享全局记忆，可用 `memory_filter` 隔离。

子代理：`task` 工具用指定预设起一个**嵌套 Loop**（全新上下文、独立预算、只回传摘要），用于「深挖一个子问题而不污染主上下文」。深度上限 2 层，需要显式开启该工具。

## 16. 风险登记册

### 16.1 最容易出错的 5 个决策点

**1. Provider 抽象的粒度：最小公分母 vs 块模型 + 能力协商**

做薄了（只抽 `chat(messages []string)`），记忆、工具、多模态全部压不进去；做厚了（一次抽象 4 类协议 + 插件式适配器），前两个月全在写适配层。

**取舍**：内核用 content block 超集模型，能力清单驱动降级，但只先实现 OpenAI 兼容 + Anthropic 两家跑通全链路；其余首期按 OpenAI 兼容接入。翻译复杂度关在适配层，运行时只认归一化事件。

**2. 上下文组装做成「每轮动态拼接」**

把当前时间、会话名、随机 ID 塞进 system 开头，或每轮重排段落——前缀缓存全废，成本翻倍、延迟上升，且没人察觉。更糟的是没有快照，质量下降时无法定位。

**取舍**：稳定前缀 + 追加式历史 + 分块压缩（不做细碎滑窗）+ 每次推理落上下文快照。把「缓存命中率」与「上下文快照」列为 M1 验收项，而不是优化项。

**3. 记忆写入策略失衡**

写太少 → 助理「记不住」，产品价值不成立；写太多 → 记忆污染、画像卡被噪音填满、注入外部错误事实，且不可回滚。

**取舍**：默认保守（显式记忆 + 定期抽取 + 会话结束总结），全部走「候选—合并」管线，带来源与置信度，可撤销、可归档不删除；外部内容一律低信任且不进画像。**宁可漏记，不可错记。**

**4. 工具权限与沙箱后置**

前几个版本只有只读工具，感觉不到痛；一旦加上文件写入与 shell，路径越狱、SSRF、注入触发的危险调用会直接造成真实损失，而补权限往往意味着重写工具协议与所有调用点。

**取舍**：从第一个工具起就带权限等级、审批接口、超时、结果截断与句柄；路径牢笼与 SSRF 防护随写类工具同时上线；审批是所有渠道的一等公民。

**5. 扩展机制的野心**

容易被「插件化」吸引，去做 Go `plugin`、动态脚本、`init()` 全局注册、运行时热更工具。Windows 上 `plugin` 支持极差，`init()` 全局状态会让测试与多实例构造变得不可能。

**取舍**：编译期显式装配 + 配置白名单；运行期唯一扩展路径是 MCP（以及数据形态的技能目录）。「写死的工具 + 可热加载的技能」已能覆盖个人助理 95% 的扩展需求。

### 16.2 次一级风险

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| 数据模型未留缝（自增 ID、硬删除、无 `updated_at`） | 将来想同步时必须重写存储层 | 统一 UUIDv7 + 软删除 + 时间戳 |
