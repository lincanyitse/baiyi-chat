## 1. 项目缘起与定位

### 1.1 缘起

市面上的 AI 助手大多有两个问题：要么是某个厂商的入口，你的对话、记忆、偏好都锁在别人的云上；要么是「一次性问答」，聊完就忘，既不懂你的历史，也不会自己找资料、调工具。

真正的个人助理应该是什么样的？中国神话里的**白泽**是一个通晓万物之情、能言人语的神兽。它知道世间万物的名字与来历，也能把所知讲给你听。这个项目想做的，就是这样一位数字助理：

- **知道得多**——不靠自己的记忆硬扛，而是能检索你的资料、查阅网络、调用工具。
- **记得住你**——跨会话记住你的偏好、经历、正在做的事。
- **能干活**——不只是聊天，能按步骤执行任务、调用外部能力。
- **属于你**——数据在本地、模型可更换、机制可修改，不绑定任何厂商。

项目名取「白泽」；代码层面使用中性的包名与二进制名，避免把神话意象带进工程细节。

### 1.2 定位

> **一个单用户、本地运行、模型无关、可持续扩展的 AI 个人助理内核。**

三个关键词：

| 关键词 | 含义 |
| --- | --- |
| **个人助理** | 服务对象是项目主人一个人。不为多用户做妥协，也不为商业化做妥协 |
| **内核** | 核心价值是一套 Agent 机制：上下文、记忆、RAG、技能、工具如何协同。UI 与渠道是可以不断更换的外壳 |
| **可持续** | 目标不是三个月做出一个 demo，而是做一个能持续用三年、持续加能力的底座 |

### 1.3 为什么值得自己做

直接使用现成的 AI 客户端并不是不行。但有三件事它们给不了：

1. **可换模型。** 今天 Claude 强，明天可能 DeepSeek 更划算，后天你换了本地显卡想跑私有模型。只有在自己的内核里，模型才是一个可替换的部件。
2. **可改机制。** 上下文怎么组装、记忆什么时候写、工具需要什么审批——这些决定了助理「像不像一个懂你的助手」。厂商不会为一个人改这些。
3. **数据属于自己。** 聊天记录、个人偏好、工作资料，不应该成为别人的训练数据或流失在某个停止服务的产品里。

## 2. 目标用户与使用场景

### 2.1 目标用户

**项目主人本人。** 一个人，一台 Windows 11 主力机，可能还有一台笔记本。具备开发能力，愿意自己配置 API Key、自己调提示词、自己写技能。

这不是一个「给家人用的产品」——至少现在不是。所有设计决策都以「一个人用得爽、改得动、维护得起」为准。

### 2.2 典型场景

| 场景 | 描述 | 依赖能力 |
| --- | --- | --- |
| **日常问答** | 随手问点什么，希望它知道你的背景，不用每次从头解释 | 记忆、上下文 |
| **资料研究** | 丢进一批 PDF / 网页，让它读完再回答，并给出出处 | RAG、引用 |
| **写作辅助** | 按你的风格改稿、续写、总结，记住你偏好的语气 | 记忆、技能 |
| **信息整合** | 「帮我查一下这几个方案的差异」——它会自己搜、自己读、自己比较 | 工具、搜索、多步推理 |
| **个人知识沉淀** | 长期积累的笔记、聊天、文档，变成一个能问的私人知识库 | RAG、记忆 |
| **流程自动化** | 把重复的事写成技能：周报生成、会议纪要整理、资料归档 | 技能、工具 |
| **随时可用** | 在手机上通过 Bot 问一句，回到家在桌面继续同一段对话 | 多渠道、共享会话 |

### 2.3 场景背后的真实诉求

用户要的不是「功能列表」，而是三件很朴素的事：

1. **不用重复交代背景。** 说过一次的事，它应该记住。
2. **答案有据可查。** 说到我的资料时，能指出是哪个文档、哪一段。
3. **能自己动手。** 查得到的东西不要让我复制粘贴，能调的工具自己去调。

这三件事分别对应记忆系统、RAG 引用、工具调用——也正是本项目的核心。

## 3. 产品原则

### 3.1 本地优先

所有数据默认存在本机：对话、记忆、知识库、配置、密钥。没有后台云同步，没有遥测上报。唯一的出站流量是主动调用模型与外部 API，且用户能查到「这次把什么发给了谁」。

### 3.2 模型无关

对话能力不由任何一家厂商定义。内核用统一的消息与事件模型，Provider 是可替换的适配器。今天用 Claude，明天换 DeepSeek，后天接本地 vLLM，记忆与知识库都不需要迁移。详见[架构纲要 §10](./03-架构纲要.md#10-provider-抽象与路由)。

### 3.3 能力可插拔

- **工具**：内置工具、MCP server、配置声明的 HTTP 工具，走同一套协议。
- **技能**：目录 + Markdown，放进 `skills/` 就能用，不用改代码、不用重新编译。
- **模型**：改配置就能加新 Provider。

新增能力不应该意味着改内核。

### 3.4 渐进披露

常驻上下文只放「永远需要」的东西。技能只露出名字和一句话，模型需要时才加载正文；记忆只放画像卡，具体事实按需检索；工具结果太长就换成句柄。

这既是节省 token 的手段，也是让模型专注的做法——上下文里塞的东西越多，指令遵循越差。

### 3.5 可换可改

代码结构要经得起「三个月后想改」：

- 分层单向依赖，改一层不影响其他层。
- 契约（消息模型、事件模型、工具协议）先定死，实现可以换。
- 每个重大决策留 ADR，三个月后还能看懂当时为什么这么做。

### 3.6 诚实面对局限

有些问题无法根治，比如提示词注入。与其假装解决了，不如明确说：真正的防线是权限分级与审批门，其他都是纵深。这种诚实会体现在文档与界面上。

## 4. 能力全景

以下按**用户视角**描述能力，不含技术细节。具体需求编号见[需求文档 §3](./02-需求文档.md#3-功能需求)。

### 4.1 对话

- 多轮流式对话，支持中断、继续、重新生成、编辑后重问。
- 可随时切换模型（质量优先 / 速度优先 / 本地优先）。
- 会话可归档、可搜索、可分支对比。

### 4.2 工具调用

- 模型可以自己决定调用工具，并把结果用于后续推理。
- 一次可并行调用多个工具。
- 危险的操作用户必须确认；只读操作自动执行。
- 支持接入 MCP 生态，复用社区已有的工具服务。

### 4.3 记忆

分四层：

| 层次 | 用户感受 |
| --- | --- |
| 工作记忆 | 「它记得我们这段对话在聊什么」 |
| 情节记忆 | 「它记得我们上个月讨论过这个项目」 |
| 语义记忆 | 「它知道我不喜欢长篇大论，知道我住在哪、做什么工作」 |
| 程序记忆 | 「它知道我做周报的习惯流程」 |

用户可显式说「记住这个」，也可查看、修改、撤销任何一条记忆。外部资料里的事实不会被当成用户的个人事实。

### 4.4 知识库（RAG）

- 三种接入方式：上传文件、给一个 URL、指定本地目录。
- 自动解析、切分、索引，支持中文检索。
- 回答时给出可点击的出处，能跳回原文位置。
- 换嵌入模型会自动重建索引，不需要手动清库。

### 4.5 技能

- 用 Markdown 写流程与知识，放进目录就生效。
- 模型自己判断什么时候该用哪个技能；也可以用 `/技能名` 强制激活。
- 技能可以带参考资料（按需读取）和脚本（执行需审批）。
- 不同场景的 Agent 预设：工作、学习、代码、闲聊，各自有不同的人格与工具集。

### 4.6 多模态

- 图片理解：截图、照片、图表可直接丢进来问。
- 文档理解：PDF、Word、Excel 通过解析服务转成可检索内容。
- 语音（后续）：语音输入转文字，回复可转语音。

### 4.7 多渠道

同一个内核，多种外壳：

| 渠道 | 定位 |
| --- | --- |
| Web | 主力使用界面，功能最全 |
| 桌面 GUI | 双击即用，常驻托盘，支持离线 |
| CLI | 脚本与管道调用 |
| Bot（飞书 / Telegram） | 手机上随时问，与桌面共享同一段对话 |

### 4.8 可观测

- 任意一轮都能看到：模型看到了什么、调用了什么、花了多少钱。
- 上下文可以逐段查看，能解释「为什么这次回答变差了」。
- 可以重放某一轮，换个模型对比效果。

## 5. 产品矩阵

### 5.1 内核一次性投入，之后是并列的产品

```
                    ┌── Web 产品      ← 当前主攻
内核（已完成）───────┼── 桌面产品      ← 托盘常驻
  M0 地基            ├── CLI 产品      ← 脚本可调用
  M1 Agent           └── Bot 产品      ← 随身可用
  M2 记忆与 RAG
```

**内核**（能对话、调工具、有记忆、能检索）是所有产品的共同基础，只做一次。它已经完成。

**之后是四个并列的产品**，各有自己的用户场景、界面形态与验收标准。它们共享内核与会话数据，但不共享界面代码，也不互相阻塞。

| 产品 | 解决什么 | 形态 | 状态 |
| --- | --- | --- | --- |
| **Web** | 坐下来认真用 | 浏览器界面 | 打磨中（[规格](./17-Web产品规格.md) / [路线图](./18-Web产品路线图.md)） |
| **桌面** | 随时待命 | 托盘常驻 + 窗口 | 探索暂存（`feature/desktop-m4`） |
| **CLI** | 脚本与管道 | 命令行 | 未启动 |
| **Bot** | 离开电脑也能用 | 飞书 / Telegram | 未启动 |

### 5.2 为什么不是「内核 → Web → 桌面 → CLI → Bot」的一条线

这条线走过一遍（M0–M4），暴露出两个问题：

**1. 「功能完成」被当成「产品完成」。** M3 的 13 项交付物完成 10 项就打了勾，但真正当产品用一遍会发现：设置口令后登录页白屏、没配模型时点发送永久卡住、会话过期后不会重新登录。这些不是「没做的功能」，是「做了但用不了」。

**2. 串行化掩盖了产品的独立性。** 把桌面排在 Web 之后，隐含「Web 定型才能做桌面」——但桌面的核心（托盘、双击启动）与 Web 的功能完整度几乎无关。串行只会让两件事互相阻塞。

详见 [ADR-0019](./adr/ADR-0019-形态路线改为产品矩阵.md)。

### 5.3 为什么仍然先做内核

聊天界面会诱导你把上下文写死在 UI 里，而不是抽象成独立模块。没有内核时，记忆、RAG、工具都会以「给 UI 打补丁」的形式长出来，最后无法复用。界面做得越早，越容易用「看起来能用」掩盖「机制不对」。

这条判断没有变——变的是「内核完成后」的组织方式：不是继续排阶段，而是并行推进各自独立的产品。

## 6. 差异化

| 维度 | 常见产品 | 白泽 |
| --- | --- | --- |
| 数据归属 | 云端账号 | 本地文件，可完整导出 |
| 模型 | 绑定自家模型 | 四类协议，随时可换 |
| 记忆 | 不透明、不可编辑 | 四层记忆，可查看、修改、撤销、溯源 |
| 知识库 | 上传即黑盒 | 混合检索、可点击引用、可换嵌入模型重建 |
| 扩展 | 官方插件市场 | 技能是 Markdown 文件，工具走 MCP 标准 |
| 可观测 | 只能看到回答 | 能看到模型看到了什么、花了多少钱 |
| 修改 | 不可能 | 代码在你手里 |

一句话：**内核是基础设施，产品是让它顺手的那层。**

M0–M3 把内核做完了——它确实不是一个产品，是一个属于你的基础设施。但从现在起，Web / 桌面 / CLI / Bot 是四个要按产品标准打磨的东西：不是「功能清单打勾」，而是「用户走得通」。

## 7. 成功标准

不做 KPI 式的量化指标，因为用户只有一个人。用下面这些更真实的标准判断：

### 7.1 使用层面

- **日常使用率**：一周内有 5 天以上主动打开它，而不是「想起来才试试」。
- **免解释率**：多数对话不需要重新交代背景，它能直接用上之前的记忆。
- **答案可信度**：涉及个人资料的问题，答案附带引用且引用准确。
- **任务完成度**：需要多步操作的事情（查资料、整理文档），它能自己走完而不是中途要你接手。

### 7.2 工程层面

- **维护成本**：加一个新 Provider、新工具、新技能，不需要改内核。
- **可恢复性**：任何一次崩溃都不丢数据，能接着上次继续。
- **可理解性**：三个月后回来看代码和文档，还能明白当时的决策。
- **成本可控**：每轮对话的成本可预期，内部任务（摘要、抽取）不烧钱。

### 7.3 反面信号

出现以下情况说明方向走偏了：

- 为了接某个厂商的特殊能力，在内核里写满了 `if provider == "xxx"`。
- 记忆越用越乱，开始出现明显错误或过时的个人信息。
- 上下文越塞越满，回答质量反而下降。
- 加新功能需要改动超过三个模块。
- 为了「看起来更强」引入一堆用不上的抽象。

## 8. 非目标

明确写出**不做什么**，比写做什么更重要。

| 非目标 | 原因 |
| --- | --- |
| 多租户 / 账号体系 | 只有一个人用。引入账号体系会污染数据模型与所有查询 |
| 计费 / 订阅 / 支付 | 不对外提供服务 |
| 运营后台 / 用户管理 | 没有用户要管理 |
| 公开 SaaS / 云端部署 | 数据必须在本地 |
| 团队协作 / 共享会话 | 个人助理的前提是「一个人的上下文」 |
| 插件市场 / 第三方开发生态 | 只有自己写技能与工具。MCP 已覆盖外部工具需求 |
| 移动原生 App | Bot 渠道已能满足移动端需求，原生 App 收益不抵成本 |
| 个人微信接入 | 无官方 API，第三方方案有封号与合规风险 |
| 自建模型推理 | Go 内不做本地推理，一律走外部 API 或本地推理服务 |
| 学习型路由 / 自动调参 | 一张配置表 + 手动覆盖，比任何自动策略都可靠 |
| 追求「全能」 | 不追求覆盖所有场景。做深记忆、RAG、工具三件事 |

## 9. 风险与应对

### 9.1 产品风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **变成「又一个聊天壳」** | 没有记忆与工具，与直接用厂商客户端无异 | 内核阶段就把记忆、RAG、工具做扎实，界面最后做 |
| **记忆污染** | 助理「记错」比「不记」更糟 | 保守写入策略、候选合并管线、来源溯源、可撤销。宁可漏记，不可错记 |
| **维护成本失控** | 个人项目最常见的死法 | 单一语言、零外部服务依赖、编译期装配、只开 6 组接口 |
| **外部 API 依赖** | 厂商涨价、停止服务、地区限制 | Provider 抽象 + 路由降级 + 本地模型兜底 |
| **成本失控** | 长期使用不可持续 | 每轮预算、内部任务走便宜模型、成本面板、价格表 |
| **功能蔓延** | 什么都想做，什么都做不深 | 明确非目标清单；每个里程碑只做一件事 |

### 9.2 技术风险

详见[架构纲要 §16 风险登记册](./03-架构纲要.md#16-风险登记册)。最需要盯住的是五个决策点：

1. Provider 抽象的粒度（块模型 + 能力协商，但只先实现两家）。
2. 上下文组装是否保护前缀缓存（稳定前缀 + 追加式历史 + 快照）。
3. 记忆写入策略（保守优先，走合并管线）。
4. 工具权限与沙箱（从第一个工具起就在协议里）。
5. 扩展机制的野心（编译期装配 + MCP，不做 Go `plugin`）。

### 9.3 渠道与合规风险

- **个人微信**：没有官方 API。第三方逆向方案存在封号风险，且可能违反平台协议。**不做。** 如有强需求，退化为企业微信应用。
- **飞书 / Telegram**：有官方 Bot API，合规。Telegram 在国内需代理，做好配置项。
- **网页抓取**：遵守目标站点的 robots 与频率限制；`web_fetch` 只做单页读取，不做爬虫。

### 9.4 隐私风险

- 对话内容会发送给所选模型厂商。这是使用云模型的固有代价，不可隐藏。
- 应对：可查看出站内容、可按厂商关闭记忆/RAG 外发、隐私模式强制本地模型。
- 密钥以环境变量或 DPAPI 加密存储，不落配置文件明文、不落日志。
